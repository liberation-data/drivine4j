# Dynamic list-membership — `ComparisonOperator.HAS_ELEMENT` — 0.0.72

Small follow-up to the dynamic-key path (0.0.69/0.0.70). Drivine has typed list-membership —
`infix fun <E> PropertyReference<List<E>>.hasItem(value: E)` → `value IN n.key` (0.0.56) — but the
dynamic-key path couldn't express it:

- `ComparisonOperator` had no reversed-membership entry (its `IN` is `n.key IN $list`, the opposite).
- `field(key)` / `property(key)` return `PropertyReference<Any?>`, which `hasItem` (needs `List<E>`) rejects.

`HAS_ELEMENT` closes that: reversed membership (`$value IN n.key`) reachable via `predicateOn` /
`predicate`, so a runtime/bagged list key works.

```kotlin
where { query.predicateOn("tags", ComparisonOperator.HAS_ELEMENT, "kotlin") }   // → $p IN n.tags
where { query.field("tags") hasElement "kotlin" }                                // infix twin, same render
where { query.property("metadata.tags") hasElement "graph" }                     // bagged → $p IN n.`metadata.tags`
```

## What it is

- **`ComparisonOperator.HAS_ELEMENT`** — renders `$param IN <lhs>` (bound value on the **left**, the
  list-valued property path on the right), the reverse of `IN` and the dynamic twin of the typed
  `hasItem` / `WhereCondition.ListMembershipCondition`. The value binds as `$param_*` (never spliced);
  the key resolves via the same model-aware path as any other `predicateOn` operator, so a dotted/bagged
  key is backtick-quoted (`$p IN n.`metadata.tags``).
- **`infix fun PropertyReference<Any?>.hasElement(value: Any?)`** — ergonomic hand-written form for an
  **untyped** reference (`property(path)` / `field(key)`), where the typed `hasItem` can't apply because
  the element type isn't known. Typed list fields keep using `hasItem`.

Rendering lives in `CypherGenerator.buildPropertyCondition` (and `buildPropertyConditionWithLhs`, which
also gained the previously-missing `NOT_IN` / `*_IGNORE_CASE` cases while I was there). No new
`WhereCondition` variant — it's a `PropertyCondition` with the new operator, so binding/`countParameters`/
`extractBindings` need no changes (it's a value-bearing, non-null op).

## Tests

- `query/dsl/DynamicPropertyPredicateTest` (unit) — `HAS_ELEMENT` renders `$param IN n.<key>` (bound,
  not spliced), a dotted bag key is backtick-quoted on the right, and the `hasElement` infix renders
  identically to the operator form.
- `manager/DynamicPropertyFilterCrossEngineTest` (Neo4j / FalkorDB / Memgraph) — a list-valued property
  filtered three ways returns the same rows: typed `hasItem`, dynamic `predicateOn(HAS_ELEMENT)`, and the
  `hasElement` infix.

## Consumer impact (`embabel-agent-rag-graph`)

embabel 1.0 added `PropertyFilter.HasElement(key, value)` — the **only** untranslatable leaf left in the
`PropertyFilter → where { }` translator (all others already map to `predicateOn` / `anyOf` / `not` /
`hasAnyLabel`). It's now one line:

```kotlin
is PropertyFilter.HasElement -> predicateOn(filter.key, ComparisonOperator.HAS_ELEMENT, filter.value)
```

completing full `PropertyFilter` coverage — tag-filtered RAG included — with no remaining Cypher fallback
(the only residual engine caveat is FalkorDB's missing `=~` for `Like`, tracked upstream at
FalkorDB/FalkorDB#2237).

## Follow-ups

None — with `HAS_ELEMENT`, the dynamic operator set covers embabel's entire `PropertyFilter` model.
