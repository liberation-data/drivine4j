## The contract

`limit(n)` and `skip(n)` push a row bound into the generated Cypher rather than over-fetching and
trimming in memory:

```kotlin
// top 20
graphObjectManager.loadAll<PropositionView> {
    orderBy { proposition.created.desc() }
    limit(20)
}

// page 3, 20 per page
graphObjectManager.loadAll<PropositionView> {
    orderBy { proposition.created.desc() }
    skip(40)
    limit(20)
}
```

Both are bound parameters — `$_limit` and `$_skip` — appended after `RETURN … ORDER BY …`, so the
statement text is identical across pages and stays cacheable in the engine's plan cache.

From Java, `.limit(n)` / `.skip(n)` sit on the query builder alongside `.where()` / `.orderBy()`.

## The key design decision: LIMIT bounds roots, not rows

For a `@GraphView`, `limit(n)` bounds **root entities**, and each returned view keeps its
relationships fully populated.

This is only true because of how views are projected: relationships are pattern comprehensions inside
the projection, so one root is exactly one row. A join-shaped query would have made `LIMIT 1` on a
root with two children return a half-populated object — the classic ORM pagination bug. Here the
cardinality question never arises, and the cross-engine test pins it: limiting to a single root that
has two mentions still returns both mentions.

Anyone changing the projection strategy away from pattern comprehensions has to revisit this
guarantee, which is the main reason this note exists.

## Semantics worth knowing

- Without `orderBy`, the subset is an arbitrary `<= n` — standard Cypher, not a Drivine choice. Pair
  `limit` with `orderBy` for a deterministic top-N.
- `count(…)` ignores `limit`/`skip` in the same spec: it answers "how many match", not "how many
  would this page return".
- `loadNearest` takes no limit — `topK` is already its bound.
- `limit(0)` returns empty; `skip` past the end returns empty. Both are asserted rather than assumed.
- `limit` and `skip` require `n >= 0`.

## Why offset pagination is not the end of the story

`skip(n)` makes the engine walk and discard `n` rows, so cost grows with page depth, and any
concurrent insert shifts every subsequent page — a row can be seen twice or skipped entirely. That is
acceptable for shallow, static result sets and poor for deep or live ones, which is what `seek`
(0.0.74) exists to solve. `seek` and `skip` are mutually exclusive by construction.
