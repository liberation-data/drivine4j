# A `saveAll` of several labels as one statement, and a batch FalkorDB cannot apply whole — 0.1.7

A store sometimes has to write nodes of two labels as one unit. Recording a processed chunk in
[embabel/dice#162](https://github.com/embabel/dice/pull/162) merges a hash node and moves a bookmark
node: if the hash is written and the bookmark is not, the chunk is skipped as processed while its
bookmark never moves.

Before 0.1.7, `StatelessGraphObjectManager.saveAll` wrote fragments of one class as one `UNWIND`
statement, and fragments of two classes as two statements, run by `queryBatch` in one transaction.
FalkorDB has no multi-statement transactions. In the default `WARN` mode a transaction there is a
pass-through: each statement commits as it runs, and a rollback only logs. A batch whose second
statement failed left the first one's writes, and nothing in the API said so.

## What changed

### Fragments of several classes are one statement

On Neo4j, FalkorDB and Memgraph, a `saveAll` of fragments alone, of any number of classes, is one
statement, where:

- each fragment can be written as a row of an `UNWIND`: not one with a `@PropertyBag` or a
  `@NodeLabels` field, nor on FalkorDB one with a `@VectorIndex` field; and
- there are no more than 1,000 of them, the rows one statement of a batch takes.

One statement is applied whole or not at all on every engine, FalkorDB included. A fragment that
cannot be written as a row is saved by statements of its own, stamped or not, and the fragments of
the batch that can are still one statement where they are of two classes or more. A batch of more
than 1,000 such fragments is written as before: a statement or more for each class.

In that statement the classes go in the order of their names, unstamped classes first, and the rows
of each in the order of their ids, so two batches over the same nodes take their locks in the same
order whatever order the caller gave them in.

Oracle is unchanged: it already wrote a batch of fragments, of any classes, as one block for each
500 of them, and runs the blocks of a batch in one transaction.

Each class is written by the `UNWIND` it has on its own, and the stamps a stamped fragment is handed
back are the same as before. A batch is not checked, as before: a stale stamp on a fragment is
written over, and the object handed back keeps a token the store's node does not vouch for.

A view is a statement of its own, as it was. A batch that holds a view is more than one statement.

### A batch FalkorDB cannot apply whole is reported, or refused

`PersistenceManager.atomicBatches` says whether a batch of more than one statement is applied whole.
It is true on Neo4j, Memgraph and Oracle, and false on FalkorDB. It is a capability to ask, as
`supportsSchemaManagement` is, rather than an engine to match. A `ConnectionProvider` declares it;
one of your own that commits each statement as it runs should say `false`.

On a store where it is false:

- **A batch of one statement runs with no transaction.** It is applied whole on its own, and a
  transaction would add nothing to that. Before, `STRICT` mode refused it, as any transaction is
  refused, so every `saveAll` and `patchAll` failed in that mode.
- **In `WARN` mode (the default), a batch of more runs statement by statement**, as before: a
  failure midway leaves the statements before it written, and nothing is undone. The first such
  batch on a manager logs a warning saying the batch is not applied whole; each later one is logged
  at debug. Nothing else tells the caller: a batch that succeeds returns as it does on any engine,
  and one that fails throws the failing statement's error with the statements before it still
  applied.
- **In `STRICT` mode, a batch of more is refused with `NonAtomicBatchException`** before any of it
  runs, and before a connection is taken. Nothing is written. `statements` says how many statements the batch would have run.

Inside a caller's transaction (`@Transactional`), the transaction is what runs the batch:

- **In `WARN` mode** a batch of more runs statement by statement on the transaction's connection,
  and is reported as above. A rollback of the caller's transaction undoes none of it.
- **In `STRICT` mode** the store refuses to start the transaction, at the first statement the
  transaction runs. A `saveAll` there is refused with the store's `UnsupportedOperationException`,
  as any statement is, whether it is one statement or more: it is not a `NonAtomicBatchException`,
  since it is the transaction that is refused and not the batch.

`NonAtomicBatchException` is an `UnsupportedOperationException`, which is what `STRICT` mode threw
for a batch before. A handler written for that still catches it.

### Why `WARN` reports and does not refuse

`falkorDbTransactionMode` already chose between running what FalkorDB cannot make atomic and
refusing it. `WARN` is documented as a pass-through, and existing code saves batches of views on
FalkorDB in that mode. Refusing every batch of more than one statement there would break that code
on upgrade. `STRICT` is the mode that refuses, and it now refuses a batch with a named exception,
before anything is written, and no longer refuses a batch of one statement. A caller that needs
`saveAll` to be all or nothing on FalkorDB either saves fragments that fit in one statement, which
is atomic in either mode, or sets `STRICT` to be told when a batch is not.

## Upgrading

- **Nothing to change** for a `saveAll` that worked before. A batch of fragments of several classes
  now sends one statement where it sent one for each class.
- **On FalkorDB in `STRICT` mode**, a `saveAll` or `patchAll` of one statement is now written where
  it was refused. One of more statements is refused with `NonAtomicBatchException` where it was
  refused with a plain `UnsupportedOperationException`.
- **A `PersistenceManager` of your own** gets `atomicBatches` from the interface, as true. Override
  it if its store cannot roll back.
- **A `ConnectionProvider` of your own** gets `atomicBatches` as true and `refusesNonAtomicBatches`
  as false. A provider whose store cannot roll back says `atomicBatches = false`, and says
  `refusesNonAtomicBatches = true` where a batch of more than one statement is to be refused rather
  than run statement by statement.

## Engine notes

FalkorDB 6 needs the statement written a particular way. Each class's `UNWIND` is folded to one row
before the next class begins, and two things that would be natural in Cypher make FalkorDB bind the
wrong node:

- carrying a count from one fold through two more fails the statement ("Type mismatch: … but was
  Integer"), so only the stamps a class hands back are carried on
  ([FalkorDB#3369](https://github.com/FalkorDB/FalkorDB/issues/3369));
- a `MERGE` after two folds, of which the later follows a `WITH`, binds the node of the `MERGE`
  before it and writes the row to that node. The rows are projected (`WITH row`) before each
  `MERGE` after the first, which FalkorDB then reads correctly
  ([FalkorDB#3368](https://github.com/FalkorDB/FalkorDB/issues/3368)).

Either workaround can be removed once FalkorDB fixes its issue.

The tests that hold these are in `StatelessSaveAllAtomicCrossEngineTest`, which runs on Neo4j,
FalkorDB and Memgraph.
