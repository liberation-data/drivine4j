# Filtered fragment `loadNearest` — 0.0.71

Maintainer handoff for follow-up #1 from 0.0.68. Filtered `loadNearest(class, Q, vector, topK, threshold)
{ where { } }` was `@GraphView`-only, while filtered `loadMatching` (0.0.68/0.0.69) and *unfiltered*
`loadNearest<Fragment>` already handle bare `@NodeFragment`s. A fragment hit the guard:

```
java.lang.IllegalArgumentException:
  loadNearest { where { } } currently supports @GraphView types; ChunkNode is not a @GraphView
```

This closes the asymmetry: **filtered `loadNearest` now accepts a `@NodeFragment`**, the exact vector
mirror of filtered `loadMatching`.

```kotlin
gom.loadNearest(ChunkNode::class.java, ChunkNodeQueryDsl.INSTANCE, vector, topK = 20, threshold = 0.7) {
    where { query.field("source") eq "wiki"; query.containerSectionId eq "sec-1" }
}   // → List<Scored<ChunkNode>>, polymorphic dispatch included
```

## What changed (small — it's a mirror)

The vector `CALL` + score-normalization head is unchanged; only the **root/index resolution +
where-rendering** needed to accept a fragment (`viewModel == null`), the way filtered `loadMatching`'s
planner already did.

- `VectorSearchPlanner.planFiltered` (`ScoredSearchPlanner.kt`) — dropped the `require(@GraphView)`
  guard and branched view-vs-fragment, identical in shape to `FullTextSearchPlanner.planFiltered`:
  - **view** → `buildWhereClause(…, viewModel, projectedCollectionMode = true)` + `GraphViewQueryBuilder.buildVectorQuery(…, whereClause)` (unchanged).
  - **fragment** → `buildWhereClause(conditions, null, grammar)` (renders against alias `n`) +
    `VectorIndexResolver.resolve(fragmentClass, …)` (the `{label}_{property}_vector` convention the
    unfiltered `loadNearest<Fragment>` already uses) + `FragmentVectorSearchBuilder.build(…, callerWhere)`.
- `FragmentVectorSearchBuilder.build` gained an optional `callerWhere: String?`, `AND`-ed with the
  threshold into the post-`CALL` `WHERE` (the same shape `FragmentFullTextSearchBuilder` already had).
  The unfiltered fragment path passes no `callerWhere`, so it is unchanged.

The `where` runs *after* the vector `CALL` binds the matched node to `n` — so `query.<field>` /
`property("metadata.key")` / `field("key")` all filter the vector-sourced node directly, no projection.
`topK` remains the index `k`; the post-filter can return fewer than `topK` rows (documented semantics).

## Tests

- `manager/FilteredFragmentVectorSearchCrossEngineTest` (Neo4j / FalkorDB / Memgraph) — filtered
  `loadNearest` over a `@VectorIndex` fragment (`VecDocNode`): a `where` on a promoted `@GraphProperty`
  field and on a `@PropertyBag` key (via both `property(...)` and the resolving `field(...)`), ranked
  closest-first, `topK`; **polymorphic dispatch** on a sealed `@VectorIndex` base (`VecContentNode` →
  `VecChunkNode` / `VecImageNode`); and a **regression** asserting the old "not a @GraphView" exception
  is gone for a fragment. Fixtures in `sample/vectorfilter/`.
  - Note: the sealed base declares a **property-target** `@VectorIndex val embedding` (not `@get:`), so
    `VectorIndexResolver` resolves it from the base type — confirmed working on all three engines.

## Consumer impact (`embabel-agent-rag-graph`)

`GraphObjectManagerStore.vectorSearchWithFilter` was the **one** retrieval method still on hand-written
Cypher, *solely* because of this gap (`textSearchWithFilter` already moved). It now becomes the exact
mirror of `textSearchWithFilter`:

```kotlin
gom.loadNearest(ChunkNode::class.java, ChunkNodeQueryDsl.INSTANCE, vector, request.topK, request.similarityThreshold) {
    where {
        metadataFilter?.let { query.applyFilter(it) }   // the 0.0.69/0.0.70 PropertyFilter → where translator
        entityFilter?.let  { query.applyFilter(it) }
    }
}.map { SimilarityResult.create(it.value.toCoreType(), it.score) }
```

The store then deletes its last filter-Cypher machinery (`CypherFilterConverter` usage,
`combineFilters`, `commonParameters`, the `RagDialect` dependency) — **100% object-manager retrieval,
zero hand-written filter Cypher**. It also fixes the same latent bagged-key bug on the vector side that
`loadMatching` fixed on the text side (the `CypherFilterConverter` nested-map limitation vs. drivine's
backtick-quoted `` n.`metadata.key` ``).

## Follow-ups

None specific — with this, both scored-search primitives (`loadNearest` / `loadMatching`) support the
full matrix: view/fragment × unfiltered/filtered, with the dynamic + model-aware key resolution from
0.0.69 / 0.0.70.
