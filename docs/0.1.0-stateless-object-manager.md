# A stateless object manager, a checked stamp, and read-only view fields — 0.1.0

`GraphObjectManager` keeps a snapshot of every object it loads or saves, and a save writes only what
differs from it. The snapshot is what that manager last saw, not what the store holds. When anything
else changes or deletes the node (plain Cypher, another manager, another process), the next save is
partial.

0.1.0 adds a manager that keeps no snapshot, and a way to refuse a save when the node has changed.

This page is the release's record: what changed, how to upgrade, and the tools that repair data saved
before it. How to use the new manager is in the README, under
[Saving Data](../README.md#saving-data) and
[@NodeStamp](../README.md#nodestamp-refusing-a-save-when-the-node-changed).

## What changed

### Breaking

- **Recompile.** Code compiled against 0.0.x must be compiled again. The loading and query methods
  of `GraphObjectManager` are now declared on `GraphObjectOperations`, and a caller compiled against
  the old class does not link. The same holds for Java callers of `JavaQueryBuilder` and the query
  starter, whose constructors now take a `GraphObjectOperations`.
- **Every node a manager saves carries `__drivine.stamp`**, and so does the node at each end of a
  relationship a manager or `edges` writes or removes, whether or not its type declares a
  `@NodeStamp` field. A node that has no stamp is given one by the first save that writes it, even
  when nothing else about it differs. It cannot be turned off. Drivine's own mapping ignores the
  property. Cypher that returns all of a node's properties, such as `properties(n)`, now returns it
  too: a test that compares a whole property map, Cypher that copies one node's properties to
  another, an export, or a class of your own that refuses unknown properties will see it. Property
  names beginning `__drivine.` are Drivine's own (`NodeLabelsModel.RESERVED_PREFIX`), should your
  code need to tell them from its own.
- **Relationships saved through an `INCOMING` field point the wrong way in the store.** A view save
  now writes a relationship in the direction its field declares. Before, it wrote every one as
  outgoing, and the view did not load an `INCOMING` field back. What is stored needs turning round:
  see [Repairing data saved before 0.1.0](#repairing-data-saved-before-010).
- **A `@GraphPath`, `@Count` or `@Aggregate` field, and a list of fragments read over several hops
  (`maxDepth` above 1), is read-only**, with either manager. A view the manager had not loaded used
  to write a path field as a direct relationship of the first hop's type, and a several-hop list as
  a direct relationship from the root to each item. Neither is written now, and what was written
  stays in the store until removed: see
  [`PathRelationshipReport`](#pathrelationshipreport).
- **A cascading delete no longer follows a read-only field.** Before,
  `delete(id, View::class.java, CascadeType.DELETE_ALL)` deleted the nodes of a `@ReadOnly` field,
  and for a `@GraphPath` field the nodes a direct relationship of the first hop's type led to.
- **A view cannot be ordered, paged by keyset, or filtered in a scored search on a root property it
  does not project.** A property that is not a declared field of the root fragment used to be read
  from the projected root as null, so the order was arbitrary and a keyset cursor skipped or
  repeated rows. It is now refused with `IllegalArgumentException`. Declare the field.
- **A recursive collection cannot be sorted in the query.** It emitted Cypher that did not run; it
  is now refused with `UnsupportedOperationException`. Use `@SortedBy`.
- **`OrderSpec` and `SeekValueSpec` paths are not rendered verbatim.** What follows the first dot
  is a property name, and is quoted unless it is a plain identifier.
- **Generated query DSL extensions have the receiver `GraphObjectOperations`**, which both managers
  implement. Calls on a `GraphObjectManager` compile as before; generate the DSL again with the
  0.1.0 generator.
- **On Memgraph, `edges.relate` and `edges.unrelate` now write to both nodes**, to mark them, so two
  calls on the same node at the same moment can conflict where before they did not. `edges` does not
  run a statement again.

### Fixed

In saves, with either manager:

- A view save through an `UNDIRECTED` field added a relationship from the root beside one already
  stored towards it. Either direction now satisfies the field.
- Relationship statements matched a node on its id field's name. They now match on the property a
  `@GraphProperty` stores the id under.
- A view whose root id is stored under another name (`@NodeId @GraphProperty("…")`) is now loaded,
  updated and deleted by id. Before, the lookup used the field's name and found nothing.
- With `GraphObjectManager`, a target with a numeric id was matched as text when a relationship to
  it was removed. A relationship dropped from a loaded view stayed, and `DELETE_ORPHAN` deleted and
  made again targets the object still held.
- With `GraphObjectManager`, `DELETE_ORPHAN` could delete the root it had just saved, through a
  relationship from the root to itself.
- The message that refuses `DELETE_ORPHAN` blamed FalkorDB, which supports it. It now names
  Memgraph, the engine without it.
- `executeBatch` did not release its connection when its transaction could not be started, as on
  FalkorDB in `STRICT` mode.

In loads and queries:

- Ordering and keyset paging on a property-bag key emitted an unquoted dotted path, which Cypher
  reads as a lookup in a nested map. The path is now quoted.
- Ordering a view, or paging it by keyset, on a root field stored under another name
  (`@GraphProperty`, or the stamp) sorted by null. So did a filter on such a field in a scored
  search over a view, and a collection sorted with APOC.
- A runtime property key that was not a plain identifier was written unquoted unless it held a dot,
  and its parameter name could be invalid. Any such key is now quoted. A key cannot end its quotes:
  a backtick in it is doubled, and so is the escape ```, which Neo4j reads as a backtick and
  which before let a key rewrite the statement's condition. An empty key is refused.
- A `@GraphProperty` name that is not a plain identifier was written into a load's projection
  unquoted.
- A collection sorted in a subquery, on a load that also had a `where`, produced `CALL { } WHERE`,
  a syntax error. The load's `WHERE` now stands directly after its `MATCH`, before the
  projection's subqueries. That also fixes Memgraph, which refused a required relationship's check
  after a sorted collection, and it means sorted collections, paths and counts are computed only
  for the roots the load keeps.
- A collection of nested views sorted with APOC was sorted by a key its maps do not have. A
  collection inside a nested view was not sorted at all on FalkorDB; it now is.
- A scored-search filter with `any` or `none` over a collection of nested views read a key the
  element does not have, and matched nothing. It now reads the nested view's root, and reaches the
  nested view's own relationships. Over a single-valued relationship it failed with a type error;
  the relationship is now read as a list of one or none.
- `not { }` around a condition on a relationship's target rendered a variable nothing bound. It is
  now one existence check for each condition.
- A where clause numbered its parameters differently from its bindings when a relationship block
  held an `or`, a null check or a label condition, or when a nested-relationship condition came
  before a direct one.
- The Kotlin code generator wrote a stored property name into generated source as it stood, so a
  name holding `$`, `%`, a quote or a backslash broke the generated file or the generator.

### Deprecated

- `GraphObjectManager` and `GraphObjectManagerFactory.get()`. Apart from the fixes above and the
  stamping below they behave as before. A build that treats warnings as errors needs the move or a
  suppression: `@Suppress("DEPRECATION")` in Kotlin, `@SuppressWarnings("deprecation")` in Java.
  The old manager's documentation is in
  [legacy-graph-object-manager.md](legacy-graph-object-manager.md).

### Added

- `StatelessGraphObjectManager`, from `GraphObjectManagerFactory.stateless()`.
- `@NodeStamp`, `StaleObjectException`, and `Stamps.setClause` / `Stamps.linksClause`.
- `@ReadOnly`.
- `GraphObjectOperations`, the interface both managers implement for loading, querying and deleting.
- `PersistenceManager.queryBatch`: `executeBatch` that returns each statement's rows. A failure of
  the batch, at commit included, is a `DrivineException`. The interface's default runs each
  statement on its own; the managers Drivine provides run them in one transaction.
- `RelationshipDirectionRepair` and `PathRelationshipReport`.

## Upgrading from 0.0.x

1. Move the core library and the code generator to 0.1.0 together, and compile again.
2. Suppress the deprecation where the old manager is still used, if warnings fail your build.
3. Deploy 0.1.0 to everything that writes to the store. A writer still on 0.0.x writes
   `INCOMING` relationships the wrong way, and path fields as relationships, again.
4. Back the store up.
5. Repair what the old saves left, as [below](#repairing-data-saved-before-010). This matters only
   for a model that has an `INCOMING` relationship field, a `@GraphPath` field or a list read over
   several hops, in a view that was ever saved.
6. Replace `factory.get()` with `factory.stateless()` and change the saves, as the
   [table](#moving-from-graphobjectmanager) says.
7. Add a `@NodeStamp` field to each type that is loaded, changed and saved. Nodes that have no
   stamp yet are covered in the README, under
   [Existing data](../README.md#existing-data).

Between steps 3 and 5 an `INCOMING` field does not load the relationships that were stored the
wrong way, and a save through it writes a new one the right way beside the old. The repair makes
one relationship of such a pair, and counts them beforehand as `collisions`.

## `StatelessGraphObjectManager`

It remembers nothing. What a save does depends on the object and the arguments, never on what was
loaded earlier. Get one from `GraphObjectManagerFactory.stateless()`.

```kotlin
stateless.save(view)                                              // add only, every non-null field
stateless.save(view, Replace(PropositionView::mentions))          // this field's list is the whole list
stateless.save(view, Replace.all())                               // every relationship field's list is the whole list
stateless.save(chunk, except = setOf(Chunk::embedding))           // write everything but these
stateless.save(person, only = setOf(Person::name))                // write just these
stateless.update<Person>(id) { it.copy(name = "Ada") }            // load, change, save what differs
stateless.edges.unrelate(from, to, "MENTIONS")
```

Loading, querying and deleting are the same on both managers: both implement
`GraphObjectOperations`. Saving is not on that interface: `save`, `saveAll` and `update` are on
`StatelessGraphObjectManager` itself, so code that saves depends on the class.

The README describes it in full. In outline:

- **A save is one Cypher statement**: the root, the relationships it drops, each related node and
  the relationship to it. It is applied whole or not at all, with or without a transaction, on
  Neo4j, FalkorDB and Memgraph. A save that is refused as stale has written nothing.
- **The statement's text does not grow with a list**: the related nodes of a field are the rows of
  one `UNWIND`. A related view, a fragment with a `@PropertyBag` or a `@NodeLabels` field, and on
  FalkorDB a fragment with a `@VectorIndex` field, still has a part of the statement to itself.
- **`save` adds relationships and removes none.** `Replace(View::field)` makes a field's list the
  whole list, and `Replace.all()` covers every relationship field of the view itself.
  `RemovedTargets.DELETE_UNREFERENCED` also deletes a removed target that nothing else refers to.
  See [Relationships](../README.md#relationships).
- **`only` and `except`** choose the root fields written.
- **`update`** is a load and a save, two statements, and writes what the change altered. It makes
  no node: if the node is gone, it returns null. See
  [Load, Change and Save](../README.md#load-change-and-save-update).
- **`saveAll`** is several statements in one transaction, or in the transaction it is called in.
  On FalkorDB, which has none, each statement is atomic and the batch is not. See
  [Batch Save](../README.md#batch-save-saveall).
- **Under `NullPolicy.CLEAR`**, a root with a `@PropertyBag` or an open `@NodeLabels` field is read
  first, for the keys and labels it holds: one more statement, which writes nothing. `update` knows
  the keys from its load. The policy governs the root; a related node is written as under `IGNORE`.
- **From Java**, fields are named as strings: see
  [Saving from Java](../README.md#saving-from-java).

## `@NodeStamp`

```kotlin
@NodeFragment(labels = ["Person"])
data class Person(
    @NodeId val id: String,
    val name: String,
    @NodeStamp val stamp: String? = null,
)
```

The field is optional and strongly recommended: without it a save is never checked. It plays the
role of JPA's `@Version`: optimistic locking, with a random value in place of a counter.

The stamp is two random tokens in one property, `__drivine.stamp`. The **data token** is replaced
when a save changes the node's properties or labels, and every save of an object that carries a
stamp compares it. The **relationship token** is replaced, at both ends, when a relationship is
added or removed or its properties change, and only a save with `Replace` compares it, because only
that save overwrites a relationship list. A save that finds what it would overwrite changed is
refused with `StaleObjectException`, and writes nothing.

The README has the whole of it: [the stamp](../README.md#the-stamp),
[when a save is refused](../README.md#when-a-save-is-refused),
[the stamp a save hands back](../README.md#the-stamp-a-save-hands-back),
[existing data](../README.md#existing-data),
[Cypher you write yourself](../README.md#cypher-you-write-yourself) and
[what a stamp does not cover](../README.md#what-a-stamp-does-not-cover).

### Cost

- The stamp is 33 characters a node.
- Replacing a stamp only when the node changes, against writing one on every save, was measured on
  Neo4j, FalkorDB and Memgraph before the stamp had two tokens: no measurable difference on a single
  save, embeddings included, and at most about 4 microseconds a node in a batch. It has not been
  measured since.
- A save of a view with a list of related nodes, on Neo4j with an index on their id, in one run:
  19 ms for 100 nodes, 64 ms for 1,000 and 136 ms for 5,000.
- Marking both ends of a relationship costs nothing measurable on Neo4j. On Memgraph, of 2,000
  statements from 8 writers at once that each joined a new node to the same node and marked both,
  about 700 were turned away and had to be run again; without the marks, none.

These are single runs on one machine, and the repository holds no benchmark that reproduces them.

## `@ReadOnly`

A view field that is loaded and never written.

```kotlin
@ReadOnly @GraphRelationship(type = "REVIEWED_BY")
val reviewers: List<Person>

@ReadOnly @GraphPath([Hop("MENTIONS", OUTGOING, label = "Person"), Hop("WORKS_AT", OUTGOING)])
val employers: List<Organization>
```

- Every save skips it, on both managers: no relationship is written and the nodes it holds are not
  saved.
- Naming it in `Replace` is an error, and `Replace.all()` leaves it alone.
- It is a choice on a `@GraphRelationship` field. A `@GraphPath`, `@Count` or `@Aggregate` field,
  and a list of fragments read over several hops (`maxDepth` above 1), is read-only whether or not
  it is declared so.
- To write along a path: `edges.relate`, Cypher, or a view rooted where the hop starts.

## Repairing data saved before 0.1.0

Three things a view save before 0.1.0 wrote are wrong in the store:

| What the old save did | What is in the store | The tool |
|---|---|---|
| wrote a relationship of an `INCOMING` field from the root to the target | a relationship pointing the wrong way, which the field does not load | `RelationshipDirectionRepair` |
| wrote a `@GraphPath` field, of a view the manager had not loaded, as a direct relationship | a relationship of the first hop's type from the root to each node the path ended at | `PathRelationshipReport.report` |
| wrote a list read over several hops as direct relationships | a relationship from the root to each node of the list, however far away | `PathRelationshipReport.reportSeveralHopLists` |

The tools go by label and relationship type. They cannot tell a relationship a save wrote from one
made some other way between the same kinds of node, so read each report before acting on it.

### The procedure

1. Upgrade every writer to 0.1.0, then back the store up.
2. Run `PathRelationshipReport.report` and `reportSeveralHopLists` over every view of the model.
   Review the findings. Run a finding's `removalStatement` where it gives one and every
   relationship counted is one to remove; deal with the rest by hand.
3. Run `RelationshipDirectionRepair.report` over every view of the model, and check that
   `unexamined` is empty.
4. Review each finding's `ambiguity`, `collisions` and `eitherWay`.
5. Run `repair` for each finding you have decided to repair. This is a step of its own, after the
   review, not something to chain to the report.
6. Report again, and expect `wrongWay` to be 0.

The path report comes first because a relationship the old save wrote for a path field also points
away from the root: turned round, it would be loaded by an `INCOMING` field of the same type.

### `RelationshipDirectionRepair`

```kotlin
val repair = RelationshipDirectionRepair(persistenceManager)

// Changes nothing. Give every view of the model.
val findings = repair.report(PersonView::class.java, IssueView::class.java)
findings.forEach {
    println("${it.view.simpleName}.${it.field}: ${it.wrongWay} wrong way, ${it.rightWay} right way, " +
        "${it.eitherWay} either way, ${it.collisions} collisions. ${it.ambiguity ?: ""}")
}
repair.unexamined(PersonView::class.java, IssueView::class.java).forEach(::println)
```

```kotlin
// Later, for a finding you have read and decided on:
val turned = repair.repair(finding)
```

**The report**

- `report` gives one finding for each `INCOMING` relationship field, in the views you pass, the
  views nested in them, and the subtype views a sealed class or `@JsonSubTypes` names. A field you
  have since declared `@ReadOnly` has one too, because the old save wrote it as it wrote every
  other. A list read over several hops has none.
- `wrongWay` counts the relationships pointing from a root to a target, which is what the old save
  wrote. `rightWay` counts those the field reads.
- `eitherWay` counts a relationship between two nodes that each carry the labels of both the root
  and the target. Either node can be the root, so it may already point the right way; it is counted
  in neither `wrongWay` nor `rightWay`. Where a view rooted at `Organization` reads `PART_OF` from a
  `Company`, a relationship between two nodes labelled `Company:Organization` is one.
- `collisions` counts the wrong-way relationships that share their two nodes with another of the
  type, pointing either way. The repair makes one relationship of them all, and where two have a
  property with different values, one value is lost.
- `unexamined` says what the report could not look at: a field whose target is an abstract view or
  an interface, where the class names no subtype and none is among the views given. A subtype
  registered only at run time, in the `SubtypeRegistry`, is not found: pass its view.

**Ambiguity.** A finding is ambiguous, and `ambiguity` says why, when the views give a reason to
think the relationships pointing away from the root are meant:

- another view declares the same relationship pointing away from the root, between nodes that can
  be the same ones. A read-only field counts, an `UNDIRECTED` one counts, and so does a view rooted
  at a subtype, whose nodes carry the root's labels too;
- a view has a `@Count` or `@Aggregate` field that reads relationships of that type pointing away
  from such a root;
- a view has a `@GraphPath` field with a hop that is stored that way, so they may be hops of the
  path;
- a view has a `@GraphPath` field, or a list read over several hops, that the old save wrote as
  that relationship. What it wrote is not this field's to load.

`ambiguity == null` reflects only the views you passed. What only Cypher or `edges` writes, no view
shows.

**The repair**

- `repair` turns round the relationships counted in `wrongWay`, keeping their properties, lists and
  temporal values included.
- Where two nodes have more than one relationship of the type between them, they become one. A
  relationship that already pointed the right way keeps every property it has and takes from those
  turned round the properties it lacks. Among those turned round, the one with the lowest id in the
  store gives its value first, whatever the batch size. Where several already pointed the right
  way, each of them takes the properties.
- `repair(finding, force, batchSize)` runs one statement for each batch, 10,000 relationships by
  default, and returns how many wrong-way relationships it dealt with: each one it turned round and
  each one it dropped for another between the same two nodes.
- Each batch is committed by itself, so a run that stops can be run again. For that reason
  **`repair` is refused inside a transaction**, with `IllegalStateException`. Call it outside one,
  with the manager `PersistenceManagerFactory.get(database)` gives by default or with one of
  `PersistenceManagerType.NON_TRANSACTIONAL`. A manager of `PersistenceManagerType.TRANSACTIONAL`
  cannot run it. `report` only reads, and any manager serves.
- `repair` refuses an ambiguous finding unless you pass `force = true`.
- A relationship turned round is not matched again, so running the repair a second time changes
  nothing.
- The node at each end of a relationship the repair deals with gets a new relationship token in its
  stamp, and a stamp if it had none. A `Replace` of an object loaded before the repair is therefore
  refused, and does not remove what the repair turned round.
- Run it once, as a migration. A relationship that was added with Cypher or `edges.relate` in the
  direction the field reads was never wrong and is left alone.

**What the tool does not repair**

- *`eitherWay` relationships* are never turned, forced or not. List them and decide each by hand.
  For a view rooted at `Organization` that reads `PART_OF` from a `Company`:

  ```cypher
  MATCH (root:Organization)-[r:PART_OF]->(target:Company)
  WHERE root:Company AND target:Organization
  RETURN root.id, target.id, properties(r)
  ```

- *A finding that is not `repairable`*: its root and its target can be the same nodes (a person who
  follows a person, or a field with a root or a target whose fragment has no label). Nothing tells
  a relationship written the wrong way from one that is meant, and `force` does not change that.
  Repair those with Cypher that knows your data, such as a property that tells the two ends apart.

Cypher of your own that turns or removes a relationship should mark both ends with
`Stamps.linksClause`, as the repair does.

### `PathRelationshipReport`

```kotlin
val paths = PathRelationshipReport(persistenceManager)

paths.report(ClaimEmployers::class.java, ClaimView::class.java).forEach {
    println("${it.view.simpleName}.${it.field}: ${it.direct} direct ${it.type} relationships. ${it.ambiguity ?: ""}")
    println("  to remove them: ${it.removalStatement ?: "no statement: read the finding"}")
}
paths.reportSeveralHopLists(ClaimEmployers::class.java, ClaimView::class.java).forEach {
    println("${it.view.simpleName}.${it.field}: ${it.direct} direct ${it.type} relationships")
}
```

It reports and does not remove. Both reports only read, so any manager serves, inside a transaction
or outside one.

- **`report`** gives one finding for each `@GraphPath` field. `direct` counts the relationships of
  the first hop's type that run from a root straight to a node of the kind the path ends at. A
  direct relationship of that type to that kind of node is often meant.
- A path finding is **ambiguous**, and says why, when one of the views declares that relationship
  (a read-only field counts), when one has a `@Count` or `@Aggregate` field that reads
  relationships of that type from such a root, or when a hop of this path or of another
  `@GraphPath` field in the views is stored as that relationship. A hop that names no label reaches
  any node. Two kinds of node can be the same when one has every label of the other, or when the
  views name a kind that has the labels of both. So pass every view of the model, and check
  `unexamined`.
- **`removalStatement`** is the Cypher that removes what the finding counted, for you to run once
  you have looked. It is null when the finding is ambiguous, and when the root or the kind of node
  the path ends at has no label, since the statement would then match relationships between nodes
  of any kind. `forcedRemovalStatement()` gives it all the same, for someone who knows that every
  relationship counted is one to remove.
- The statement removes every relationship counted, whether a save wrote it or not. It is one
  statement and not batched. It gives the node at each end a new relationship token, and a stamp if
  it had none, so a `Replace` of an object loaded before the removal is refused.
- **`reportSeveralHopLists`** gives one finding for each list read over several hops, with the
  count of direct relationships from a root to a node of the kind the list holds. It gives no
  statement to remove them: where the field is read away from the root, the first hop of what it
  reads is such a relationship too, and nothing in the store tells the two apart. Where the field
  is `INCOMING`, a relationship counted points away from the root and is not one the field reads.

## Moving from `GraphObjectManager`

The reasons are in the README, under
[Migrating from GraphObjectManager](../README.md#migrating-from-graphobjectmanager).

| With `GraphObjectManager` | With `StatelessGraphObjectManager` |
|---|---|
| `factory.get()` | `factory.stateless()` |
| `save(obj)` of a new object | `save(obj)` |
| load, change a field, `save` | `update(id) { it.copy(...) }`, or `save` of the loaded object |
| load, drop an item from a list, `save` | `update(id) { ... }`, or `save(obj, Replace(View::field))` |
| `save(obj, CascadeType.DELETE_ORPHAN)` | `save(obj, Replace(View::field, removedTargets = RemovedTargets.DELETE_UNREFERENCED))` |
| `save(obj, CascadeType.PRESERVE)` | `save(obj)` |
| `save(obj, CascadeType.DELETE_ALL)` | no equivalent: `Replace` the field, then `delete` each node dropped |
| `clearSession()` | not needed |

- `DELETE_UNREFERENCED` deletes a removed target that nothing else refers to the way the field did.
  `DELETE_ORPHAN` deletes one with no relationship in either direction. A removed target that
  nothing points at, and that points at something itself, is deleted by the first through an
  outgoing field and kept by the second.
- `GraphObjectManager` marks the stamp of each node it changes, and of both ends of each
  relationship it makes, removes or changes the properties of. A relationship it finds as it would
  write it is left unmarked. It neither checks a stamp nor hands one back.
- Every test of `GraphObjectManager` in this repository has a mirror that runs on the stateless
  manager, but for four that save with `CascadeType.DELETE_ALL`, which has no equivalent, and a
  comparison test runs the same scenarios through both and compares the graphs.

## Engines

Everything here is verified on Neo4j, FalkorDB and Memgraph. `CascadeType.DELETE_ORPHAN` on
`GraphObjectManager` remains unavailable on Memgraph; `DELETE_UNREFERENCED` is available there.
Nothing here has been run against Neptune.

- **Contention.** On Neo4j and Memgraph a stateless `save`, `update` or `saveAll` that the engine
  turns away, because another writer was changing the same node at that moment, is run again: six
  attempts in all. A checked save is then refused as stale. `edges` and `GraphObjectManager` do not
  run a statement again, and the engine's error reaches the caller. Only such a conflict is run
  again: a lost connection is not, since the save may have been applied.
- **FalkorDB** runs one write at a time and turns none away. It has no transactions: a save is one
  statement and atomic, an `update` is two statements, and a `saveAll` is several, of which those
  that ran before a failure or a refusal stay applied. With `falkorDbTransactionMode` set to
  `STRICT` a batch is refused, as any transaction is.
