# `FULLTEXT_INDEX` schema item kind — 0.0.60

Maintainer handoff for the full-text index kind added to Drivine's schema feature. Fulltext is now a
first-class managed `SchemaItemKind` alongside `VECTOR_INDEX`, `RANGE_INDEX`, and
`UNIQUENESS_CONSTRAINT` — declarable as a spec or an annotation, ensured / drift-checked / recreated
through the same orchestration, and verified end-to-end on Neo4j, FalkorDB, and Memgraph.

```kotlin
// Spec form
SchemaCatalog.of(
    FullTextIndexSpec("Chunk", listOf("title", "body")),           // multi-property
    FullTextIndexSpec("Chunk", "summary", analyzer = "english"),   // single, explicit analyzer
)

// Annotation form
@NodeFragment(labels = ["Chunk"])
@FullTextIndex(properties = ["title", "body"])       // class-level, multi-property
data class ChunkNode(
    @NodeId val id: String,
    @FullTextIndex val summary: String,              // property-level, single
    val title: String,
    val body: String,
)
```

## What it does

Adds `FullTextIndexSpec(label, properties, name?, analyzer?)` — an `IndexSpec`, so it flows through
`SchemaCatalog.items` (`indexes + constraints`), `IndexManager.ensure/find/recreate/drop`, and
`SchemaManager` exactly like the range and vector kinds. Multi-property like `RangeIndexSpec` (unlike
single-property `VectorIndexSpec`). `defaultName()` → `"${label}_${properties.joinToString("_")}_fulltext"`.

## Design decisions (and why)

- **Multi-property, one spec.** A fulltext index over `[title, body]` is one searchable analyzed
  field, so it is modelled as a single spec with a property list — matching how Neo4j and Memgraph
  natively express it. FalkorDB, which has no multi-property fulltext primitive, decomposes it (below).

- **`analyzer` is drift *only where the engine reports it back*.** `matchesShape` now follows one
  uniform rule for every shape attribute: **null on the introspected side means "unobservable", not
  "mismatch".** A `FullTextIndexSpec.analyzer` is treated as drift only when the spec sets one *and*
  introspection surfaces one to compare against. Neo4j is the only engine that both accepts an
  analyzer and reports it (`fulltext.analyzer` in the index `options.indexConfig`); FalkorDB and
  Memgraph report null, so a spec's analyzer is silently unverified there rather than drifting
  forever. This is the "never report drift we can't observe" principle the vector `similarity`
  attribute already used — generalized in the `matchesShape` KDoc.

- **Empty `indexConfig` when no analyzer.** On Neo4j, a spec with no analyzer emits
  `OPTIONS {indexConfig: {}}` and lets the engine apply its own default (`standard-no-stop-words`),
  rather than hard-coding a default that could drift across Neo4j versions.

- **Explicit names honoured where supported; the consumer binds them as parameters.** Neo4j and
  Memgraph fulltext indexes are named, and `effectiveName` / an explicit `name` is respected — this
  matters for the RAG consumer, which binds the index name as a query parameter (`$fulltextIndex`)
  and needs the created name to be predictable. FalkorDB fulltext indexes are unnamed
  (`supportsNamedItems = false`), so `name` is ignored there and `SchemaItemInfo.name` is null.

## The FalkorDB per-property reassembly (the fiddly part)

FalkorDB has no named, multi-property fulltext primitive. It exposes:

```cypher
CALL db.idx.fulltext.createNodeIndex('<Label>', '<prop>')   -- one property per call
```

and rejects re-indexing an already-fulltext property (`Attribute 'x' is already indexed`) — exactly
like its range path. So `createIndex`:

- Emits **one procedure call per property** *missing* from the label's existing fulltext coverage
  (using the `existing: SchemaItemInfo?` the manager already passes, identical to the range/vector
  logic). Extending `[name]` to `[name, description]` emits only the `description` call.
- On **introspection**, `parseIndexRows` fans a single `db.indexes()` row (one row per label, whose
  `types` map marks each property's index types) back into **one** `FULLTEXT_INDEX` item covering
  *all* `FULLTEXT`-typed properties of the label. Without this reassembly, a `[title, body]` spec —
  created as two calls — would never match one introspected item and would report drift on every
  `ensure`. `matchesIdentity` uses coverage (`containsAll`), not set-equality, for the same reason
  range does.
- **Drop** is per-property: `DROP FULLTEXT INDEX FOR (n:<Label>) ON (n.<prop>)`, so dropping a
  fulltext index never disturbs a range index (or another property's fulltext) on the same label.

A property can legitimately carry both `[RANGE, FULLTEXT]`; the range and fulltext fan-outs read the
same row independently and produce two distinct items, one per kind.

## Backend support

| Engine   | Create DDL | Named | Multi-prop | Analyzer | Status |
|----------|-----------|-------|------------|----------|--------|
| Neo4j 5  | `CREATE FULLTEXT INDEX \`<name>\` IF NOT EXISTS FOR (n:<Label>) ON EACH [n.<p1>, n.<p2>] OPTIONS {indexConfig: {\`fulltext.analyzer\`: '<a>'}}` | ✅ | ✅ native | ✅ emitted + drift-checked | ✅ verified |
| Memgraph | `CREATE TEXT INDEX <name> ON :<Label>(<p1>, <p2>)` (note: `TEXT`, not `FULLTEXT`; no `IF NOT EXISTS`) | ✅ | ✅ native | ⚠️ ignored (not reported back) | ✅ verified |
| FalkorDB | `CALL db.idx.fulltext.createNodeIndex('<Label>', '<prop>')` — one call per missing property | ✗ unnamed | ⚠️ decomposed to per-property calls, reassembled on read | ⚠️ ignored | ✅ verified |
| Neptune / openCypher | `UnsupportedSchemaGrammar` throws, as for every other kind | — | — | — | ✅ throws |

### Introspection shapes (verified against live containers)

- **Neo4j** `SHOW INDEXES` → `type = "FULLTEXT"`, analyzer at `options.indexConfig["fulltext.analyzer"]`.
- **Memgraph** `SHOW INDEX INFO` → positional row `["label_text (name: <name>)", "<Label>", ["<p1>","<p2>"], <count>]`.
  The index name is parsed out of the type string; the label may arrive colon-prefixed on 3.11+ and
  is normalized like the other Memgraph kinds.
- **FalkorDB** `CALL db.indexes()` → one row per label, `types` map e.g. `{title: [FULLTEXT], age: [RANGE, FULLTEXT]}`.

## Code map

- `SchemaItemKind.FULLTEXT_INDEX` — the new enum constant.
- `FullTextIndexSpec` — the spec (`IndexSpec`, multi-property, `analyzer?`).
- `@FullTextIndex` — the annotation (property-level single, class-level `@Repeatable` multi, with
  `name` / `analyzer`); scanned by `FragmentSchemaScanner`.
- `SchemaItemInfo.analyzer` — introspected analyzer (null where unobservable); `fromSpec` branch.
- `SchemaGrammar.matchesShape` — analyzer-drift rule + generalized "null = unobservable" KDoc.
- `Neo4jSchemaGrammar` / `MemgraphSchemaGrammar` / `FalkorDbSchemaGrammar` — create/drop/list/parse.
- `IndexManager.list()` — now queries the fulltext kind too.

## Consumer migration note

The RAG consumer binds the fulltext index name as a query parameter (`$fulltextIndex`). On Neo4j and
Memgraph, pass an explicit `name` on the spec/annotation and query with that same name — do not rely
on the derived `${label}_..._fulltext` if the consumer already has a bound name. On FalkorDB the
index is unnamed and fulltext queries address it by label/property, so no name binding applies there.
