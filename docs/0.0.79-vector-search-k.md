# 0.0.79 — `searchK`: widening the vector search without widening the result

`k` handed to a vector index is the **HNSW search beam width**, not merely a row count. `searchK` lets a
caller widen the search and still get back the number of rows they asked for.

## The evidence

On a ~9K-vector index (1536-dim, cosine), after bulk-ingesting ~2K tightly-clustered vectors: a vector
verified as true global rank 3 — by exhaustive `vector.similarity.cosine` — was **not returned at any
k ≤ 100**, and came back at rank 3 at **k = 200**. Reproduced across two full index rebuilds, with
quantization on and off, and across a database restart.

That result proves the mechanism rather than suggesting it. If `k` only limited rows, a vector at true
rank 3 would appear at k = 100 — it is comfortably inside 100. The only way k = 200 finds it and k = 100
does not is if `k` drives the candidate queue. In Lucene-backed HNSW the result queue *is* the candidate
queue, so `ef_search == k`, and Neo4j exposes no separate knob.

Two consequences:

- **Raising `k` is the only query-time lever on recall.** An "over-fetch multiplier" and "an
  effective-k knob" are therefore the same lever, not two options.
- **Under-recall here is a tunable tradeoff, not a defect.** Dense clusters saturate every neighbour
  list: with `M = 16`, near-duplicate vectors consume all sixteen links with intra-cluster neighbours,
  pruning the long-range links greedy descent needs to enter or leave the cluster. Low `ef` cannot then
  recover. Raising `hnswM` / `hnswEfConstruction` attacks that cause directly — see
  [0.0.79-vector-index-tuning.md](0.0.79-vector-index-tuning.md).

## The compounding problem: post-filter dilution

`where {}` predicates apply **after** the index yields, so a scoped caller receives roughly
`k × selectivity` rows. At 22% selectivity, asking for 40 returns about **9** — and those survivors are
the intersection of "globally nearest" with "in scope", which is not "nearest within scope".

## Usage

```kotlin
// search with a beam of 200; return the best 40 that survive the filter
graphObjectManager.loadNearest<PropositionView>(dsl, queryVector, topK = 40, searchK = 200) {
    where { proposition.contextId eq ctx }
}
```

`searchK` is what the **index** is asked for. `topK` becomes a post-filter `LIMIT`.

This is the familiar fetch-200-trim-40 workaround, with the trim in the correct place: **after** the
`WHERE`. Trimming before the filter would discard exactly the rows over-fetching was meant to recover.

Emitted shape:

```cypher
CALL db.index.vector.queryNodes('Proposition_embedding_vector', $_vectorTopK, $_vectorQuery)
YIELD node, score
WITH node AS n, score AS _score
WHERE n.contextId = $p0
RETURN { value: {…}, score: _score } AS row
ORDER BY _score DESC
LIMIT $_vectorRowLimit
```

with `_vectorTopK = 200` and `_vectorRowLimit = 40`.

## Properties worth knowing

- **Off by default is a genuine no-op.** Omit `searchK` and the emitted Cypher is byte-identical to what
  an untuned search has always produced — no stray `LIMIT`, no extra binding. Pinned by a test, because
  "we added a knob and every existing query changed shape" is its own risk.
- **`searchK < topK` throws.** It would ask the index for fewer rows than the caller wants back, which
  can only lose results — a mistake rather than a tuning choice.
- **Available everywhere the search is.** Manager API, reified extensions, and the codegen'd per-view
  wrapper — a filtered view search is the case that needs it most, and a knob unreachable from the
  generated extension is not a knob.

## What Drivine deliberately does not do

No automatic over-fetch multiplier, no adaptive top-up loop that retries with a larger `k`, no
exact-scan fallback threshold. Each would have Drivine choosing a cost/correctness tradeoff from a
selectivity estimate it does not have — the same rule that stops it substituting its own HNSW defaults.
The knob is explicit; the policy is the caller's.

## If recall is poor, in order

1. **Measure.** Exhaustive `vector.similarity.cosine` for ground truth, then compare against the ANN
   result at a range of `k`. Everything else is guesswork without this.
2. **Raise `searchK`.** Free to try, no rebuild.
3. **Raise `hnswM` / `hnswEfConstruction`** and rebuild — attacks the cluster-navigation cause rather
   than the symptom, at the cost of index size and build time.

Steps 2–3 address under-recall. They do **not** address dilution: even with perfect recall, a `k` of 40
over a whole index filtered to one scope still yields about `40 × selectivity` rows.
