# Generated `loadNearest { where { } }` view extension — 0.0.54

Closes follow-up #3 from `docs/query-features-0.0.48.md`. The codegen now emits a per-`@GraphView`
reified `loadNearest` extension that injects the view's `…QueryDsl.INSTANCE`, matching the ergonomics
of the generated `loadAll { }`.

> **Also in this build:** an audit found `count` was the one remaining DSL method still requiring
> `…QueryDsl.INSTANCE` (it had a hand-written reified `count<T, Q>(queryObject, spec)` but no generated
> wrapper). The codegen now emits `count(spec)` per view too — **ungated** (count applies to any view),
> so `count<RaisedAndAssignedIssue> { where { } }` works without `INSTANCE`. With this, every
> DSL-spec method — `loadAll`, `deleteAll`, `count`, `loadNearest` — has a generated INSTANCE-injecting
> form.

```kotlin
// before — had to pass both type args + INSTANCE
graphObjectManager.loadNearest<PropositionView, PropositionViewQueryDsl>(
    PropositionViewQueryDsl.INSTANCE, vector, topK = 20, threshold = 0.7
) { where { proposition.contextId eq ctx; mentions.any { resolvedId eq id } } }

// now
graphObjectManager.loadNearest<PropositionView>(vector, topK = 20, threshold = 0.7) {
    where { proposition.contextId eq ctx; mentions.any { resolvedId eq id } }
}
```

## What's generated

For each `@GraphView` whose **root fragment has a `@VectorIndex`**, alongside the existing
`loadAll`/`deleteAll` extensions (same generated file):

```kotlin
public inline fun <reified T : PropositionView> GraphObjectManager.loadNearest(
    vector: List<Float>,
    topK: Int,
    threshold: Double? = null,
    noinline spec: GraphQuerySpec<PropositionViewQueryDsl>.() -> Unit,
): List<Scored<T>> = loadNearest(T::class.java, PropositionViewQueryDsl.INSTANCE, vector, topK, threshold, spec)
```

Exactly the wrapper pattern the generated `loadAll(spec)` already uses, delegating to the existing
`loadNearest(graphClass, queryObject, vector, topK, threshold, spec)` manager method.

## Decisions

- **Only the filtered (spec) form.** The non-filtered `loadNearest<T>(vector, topK, threshold)` is a
  hand-written reified extension (`GraphObjectManagerExtensions`) needing no query object — not
  regenerated.
- **Gated on `@VectorIndex` on the root fragment** (the chosen option). A view with no embedding
  can't be searched (the runtime `VectorIndexResolver` would throw), so no `loadNearest` is emitted
  for it — verified: `SampleVectorView` gets one, `RaisedAndAssignedIssue` does not.
- **No overload clash.** The generated `loadNearest(vector, topK, threshold, spec)` (no queryObject,
  has a spec lambda) is distinct from the hand-written `loadNearest<T>(vector, topK, threshold)` (no
  spec) and the manager `loadNearest<T, Q>(queryObject, …, spec)` (queryObject first). Confirmed:
  `loadNearest<SampleVectorView>(vec, topK) { … }` binds to the generated one, and the sample module
  compiles it.
- **Kotlin codegen only.** The Java APT path uses the fluent `JavaQueryBuilder`, not generated
  extension functions; a Java `loadNearest` builder method is a possible follow-up.
- **Property-disambiguation variant out of scope** — multi-embedding views use the explicit method
  (the manual filtered form has no property variant either). Follow-up.

## Code

- `drivine4j-codegen/.../QueryDslGenerator.kt` — `generateLoadNearestExtensionFunction` (mirrors
  `generateLoadAllExtensionFunction`), added to the view's file when `rootFragmentHasVectorIndex(...)`
  is true. KotlinPoet auto-imports `Scored`, `GraphQuerySpec`, `List<Float>`, etc.

## Tests

- `drivine4j-sample/.../GeneratedLoadNearestTest` — asserts the **real KSP-generated** source:
  `SampleVectorViewQueryDsl` contains the `loadNearest` extension with the right `…INSTANCE`
  delegation; `RaisedAndAssignedIssueQueryDsl` (non-vector) contains none. The sample module also
  compiles the generated code (proving imports + no ambiguity).
- `manager/FilteredVectorSearchNeo4jTest` — a Neo4j round-trip calling the generated-shape wrapper
  (`loadNearest<PropositionView>(QUERY, topK) { where { property + any{} } }`) and asserting identical
  `Scored<T>` results to the explicit `loadNearest(graphClass, INSTANCE, …)` call. (The underlying
  filtered `loadNearest` is already cross-engine tested; this proves the wrapper delegates.)
