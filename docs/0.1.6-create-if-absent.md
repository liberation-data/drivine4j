# 0.1.6 — `create`: make a node only if it is not there

A store that keeps an aggregate per id needs "make it if it is not there, otherwise merge into it",
and the first write of an id must not overwrite a concurrent first write of the same id.
`StatelessGraphObjectManager` had no way to say the first half. `update(id) { }` merges into a node
that is there, and makes none. A `save` of an object with no stamp is not checked, so two writers
that each load null and each save write the same node, and the second overwrites the first.

`create(obj)` makes the node only if no node has its id, in one statement. If one does, it writes
nothing and returns null, and the caller falls back to `update`:

```kotlin
val stored = sgom.create(p) ?: sgom.update<Proposition>(p.id) { it.merge(p) }
```

How to use it is in the README, under
[Create If Absent](../README.md#create-if-absent-create).

## The API

```kotlin
fun <T : Any> create(obj: T): T?
```

- It returns the object carrying the whole stamp the save left, as `save` does, or null when a node
  has the id.
- When the node is there, nothing is written: not the root, not a related node, not a relationship,
  not the stamp.
- A view is made as `save` makes it. A related node is written unchecked, as `save` writes it.
- An object that carries a stamp is refused with `IllegalArgumentException` before anything is
  written. A stamp comes from a node that was loaded, and `create` makes one that is not there.

### Why null, and not an exception or a flag on `save`

The other choices were `save(obj, ifAbsent = true)`, and a named exception for a node that is
there. `create` returning `T?` was chosen because:

- It composes with `update`, which already returns `T?` for "no such node": the two halves of the
  upsert are each a call that answers null when its case does not hold, joined by `?:`. A Java
  caller tests for null, as for `update`.
- A node that is there is the expected answer half the time, not a failure. An exception would
  make the upsert a `try`/`catch`.
- A flag on `save` would sit beside `relationships`, `nullPolicy`, `only` and `except`, most of which
  mean nothing for a node that is made: `Replace` removes nothing from a new node, `CLEAR` clears
  nothing on it, and `only` would make a node holding part of an object. And `save` returns `T`, not
  `T?`, so the flag would change its return type.

## How each backend makes the node only if it is absent

The root's part of the save statement is what changes; the rest of the statement is the save's.

**Neo4j, FalkorDB and Memgraph** (Cypher). The root is merged, marked if the statement made it, and
the statement goes on only from a node it made:

```cypher
MERGE (n:Claim {id: $p0_id})
ON CREATE SET n.`__drivine.made` = true
WITH n WHERE n.`__drivine.made` IS NOT NULL
...
REMOVE n.`__drivine.made`
```

The mark is the one a save already uses to tell a node it made from one it found, for the stamp it
hands back. It is set and removed in the same statement. A node that was there gives no row, so no
later part of the statement runs and nothing is written.

**Oracle** (one PL/SQL block). The root's `node` step carries `absent`. A node the step finds,
locked, raises the block's refusal before anything is written, and the block gives no row, as it
does for a stale checked save. Where a uniqueness constraint refuses the insert because another
writer made the node at the same moment, the step finds that writer's node, as a save does, and so
refuses too.

**No row, or a refusal.** The manager reads no row from a statement that only makes its root as "the
node is there", and returns null. If the statement fails, it has written nothing, and the manager
reads the node: if it is there now, another writer made it at the same moment and a uniqueness
constraint refused this one (on Memgraph, "Unable to commit due to unique constraint violation"), so
it returns null. The engine's error is not read, since it differs from engine to engine. Where the
node is not there, or cannot be read, the failure is thrown.

## Two writers at the same moment

Both find the node absent, as two `MERGE`s do. Whether the second makes it again depends on the
engine:

| Engine | Without a uniqueness constraint on the id | With one |
|---|---|---|
| Neo4j | both can make a node | the second waits for the first, finds its node, returns null |
| Memgraph | both can make a node | the second is refused at commit, finds the first's node, returns null |
| Oracle | both can make a node | the second is refused at insert, finds the first's node, returns null |
| FalkorDB | the second finds the first's node: writes run one at a time | the same |

So, on every engine, declare one:

```kotlin
persistenceManager.constraints.ensure(UniquenessConstraintSpec("Proposition", "id"))
```

The test `concurrent first writes of one id all end up in the one node` runs four writers of one id
at once, ten rounds, each `create(f) ?: update(f.id) { it.merge(f) }`, on all four engines with the
constraint, and checks that every writer's data is in the one node. The same test with the
load-then-`save` the issue describes fails on all four.

On Memgraph inside a caller's transaction the constraint is checked when the transaction commits,
so the second of two transactions that each made the node fails at its commit and not at its
`create`. Running that transaction again, its `create` returns null. The test `a create in a
transaction that began before another writer made the node makes no second node` shows this on
Memgraph, and on the other engines that the `create` finds the other writer's node and returns null.

## What a save statement says about its root

A save, an update and a create differ only in which root the statement writes. That is one value,
`RootMode`, carried from the request to the statement and, on Cypher engines, to the stamping the
root's part is built with:

| `RootMode` | Root not there | Root there | Used by |
|---|---|---|---|
| `EITHER` | made | written | `save` |
| `FOUND` | no row | written | `update` |
| `ABSENT` | made | no row | `create` |

The nodes a view reaches through a relationship are always `EITHER`, unchecked, whatever the root
is held to.

## Upgrading

Nothing changes for existing callers. `create` is new, on `StatelessGraphObjectManager` alone.
