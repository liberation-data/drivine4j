# 0.0.79 — Pinning a vector index's physical configuration

Vector DDL emitted only `dimensions` and `similarity_function`, leaving everything else to the server.
Neo4j 2026.04 fills in `vector.quantization.enabled: true`, `hnsw.m: 16`, `ef_construction: 100` — not
what earlier versions used. The same declaration therefore produced a **different physical index per
server**, silently, and the difference surfaced only as a recall or latency change nobody could
attribute to anything.

Pinning makes a declared schema reproducible across engine versions.

## Two layers

**Portable** — `hnswM` and `hnswEfConstruction`. HNSW is genuinely the same algorithm in Neo4j and
FalkorDB, so these mean the same thing on both. This is not a lowest-common-denominator compromise; it
is the part that is actually common. They are the only tuning `@VectorIndex` expresses:

```kotlin
@NodeFragment(labels = ["Proposition"])
data class PropositionNode(
    @NodeId val id: String,
    @VectorIndex(similarity = SimilarityFunction.COSINE, hnswM = 32, hnswEfConstruction = 200)
    val embedding: List<Float>? = null,
)
```

Annotation attributes cannot be null, so `0` — the default — means "engine default".

**Engine-specific** — quantization is a Neo4j concept, `efRuntime` a FalkorDB one. Pretending otherwise
would either invent a lowest common denominator or leak one engine's vocabulary into every other. These
are declared only in a hand-written catalog spec:

```kotlin
SchemaCatalog.of(
    VectorIndexSpec("Proposition", "embedding", 1536,
        hnswM = 32,
        engineOptions = listOf(
            Neo4jVectorOptions(quantizationEnabled = false),
            FalkorDbVectorOptions(efRuntime = 10),
        )),
)
```

Each grammar reads only `optionsFor(its own engine)`. Options addressed elsewhere are ignored **without
warning** — declaring Neo4j options does not make a FalkorDB deployment incorrect, and warning about it
would train people to ignore the warning. One catalog therefore serves a mixed deployment with no
per-engine conditionals.

Where an engine option duplicates a portable one, the engine value wins **on that engine** and the
portable value still applies everywhere else — one declaration can say "m = 16 generally, 32 on Neo4j".

A portable pin an engine *cannot* express (Memgraph has no equivalent) is reported through
`SchemaGrammar.unsupportedVectorTuning` and logged, rather than dropped silently.

## Declaring the same index twice

An index that is both **queried** and **tuned** is necessarily declared twice: `@VectorIndex` must stay
on the fragment because `VectorIndexResolver` resolves vector queries from it, while engine options need
a catalog spec. The two meet in `SchemaCatalog.deduplicate`, which compares specs to each other with no
database involved — so drift cannot arbitrate, and plain equality would reject the pair as a conflict.

The rule:

- Declarations must agree on everything **portable** — dimensions, similarity, name, HNSW pins.
  Disagreement is a conflict and fails fast, as it always has.
- The declaration carrying **engine options wins whole**. No field-by-field merging.
- Two declarations that *both* pin engine options are a genuine conflict.

## Drift, and what is deliberately not drift

**Unpinned is never drift.** With no declared value there is nothing for the database to differ from,
and the alternative would drift every index the moment a server changed its defaults — the exact failure
this feature exists to prevent, inverted.

A **pinned** value the engine contradicts *is* drift. `ensure` reports it and changes nothing; closing it
needs `recreate()`, which rebuilds the index — and rebuilding a vector index reindexes stored embeddings
without re-embedding them. Adding a pin to an existing index is therefore an operational decision, not a
config tweak.

**Drivine never substitutes its own defaults.** Hard-coding a "safe" `m` would freeze whatever this
version of Drivine believed the engine default was, which is the same class of bug one layer up.

## Effective config is logged after every create

```
Vector index Proposition_embedding_vector on Proposition[embedding] effective config
  (engine defaults): dimensions=1536, similarity=COSINE, quantization.enabled=true,
  hnsw.m=16, hnsw.ef_construction=100
```

Pinned or not, this records what the server actually chose, so the value is attributable later instead
of becoming a suspect to be chased during an incident.

## FalkorDB: verified by readback, not by a successful CREATE

FalkorDB spells the HNSW parameters `M` / `efConstruction` and adds `efRuntime`. Those names are
confirmed by reading the values back, because **FalkorDB silently accepts unknown `OPTIONS` keys** — an
index created with a made-up key is accepted and comes back carrying FalkorDB's defaults (`M=16`,
`efConstruction=200`, `efRuntime=10`) with no trace of the key and no error. "It applied cleanly" is
therefore not evidence of anything there.

It does report all three through `db.indexes()`, so pinned values are checkable and drift detection
works on FalkorDB as well as on Neo4j.

## Upgrade note

`inventoryKey` embeds the effective name, so a spec that previously carried a blank name changes key
across this upgrade. Existing `_DrivineSchema` markers hold the old key and will produce a one-time
orphan warning on next boot. Non-destructive — orphans are reported, never dropped.
