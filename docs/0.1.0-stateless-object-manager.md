# A stateless object manager, a checked stamp, and read-only view fields — 0.1.0

`GraphObjectManager` keeps a snapshot of every object it loads or saves, and a save writes only what
differs from it. The snapshot is what that manager last saw, not what the store holds. When anything
else changes or deletes the node (plain Cypher, another manager, another process), the next save is
partial.

0.1.0 adds a manager that keeps no snapshot, and a way to refuse a save when the node has changed.

## What breaks

- A `@GraphView` that declares a `@GraphPath`, `@Count` or `@Aggregate` field must also declare it
  `@ReadOnly`. Without it the view's model fails to build, naming the field.
- A view save now writes a relationship in the direction its field declares. A field declared
  `INCOMING` used to be written as outgoing, and the view did not load it back. Relationships saved
  that way point the wrong way in the store and need turning round.
- A view the manager had not loaded used to write a `@GraphPath` field as a direct relationship of
  the first hop's type. It is no longer written.
- Every node an object manager changes now carries the property `__drivine.stamp`.
- Generated query DSL extensions have the receiver `GraphObjectOperations`, which both managers
  implement. Calls on a `GraphObjectManager` compile as before.

## `StatelessGraphObjectManager`

It remembers nothing. What a save does depends on the object and the arguments, never on what was
loaded earlier. Get one from `GraphObjectManagerFactory.stateless()`.

```kotlin
stateless.save(view)                                              // add only, every field
stateless.save(view, Replace(PropositionView::mentions))          // this field's list is the whole list
stateless.save(view, Replace.all())                               // every relationship field is
stateless.save(chunk, except = setOf(Chunk::embedding))           // write everything but these
stateless.save(person, only = setOf(Person::name))                // write just these
stateless.update<Person>(id) { it.copy(name = "Ada") }            // load, change, save what differs
stateless.edges.unrelate(from, to, "MENTIONS")
```

Loading, querying and deleting are the same on both managers: both implement
`GraphObjectOperations`.

### Relationships

- `Add`, the default, adds the relationships the object holds and removes none.
- `Replace(fields)` names the relationship fields whose list is the whole list. A relationship the
  list does not hold is removed. Fields are named because an empty list cannot tell "there are none"
  from "not set".
- `Replace` removes only what the field loads: relationships of its type and direction, to nodes with
  its target's labels. Two fields can share a relationship type.
- `Replace(field, removedTargets = RemovedTargets.DELETE_UNREFERENCED)` also deletes a removed target
  that no relationship points at. It works on Neo4j, FalkorDB and Memgraph.
- `Replace.all()` covers every relationship field. It is refused for an object that carries no
  stamp: the lists of an object built from scratch are its defaults, not what the store holds.
- `Replace` trusts that the list came from the object manager's own load. A list cut short by a
  custom query is taken as the whole list.
- `edges.unrelate(from, to, type)` removes one relationship; `edges.unrelateAll(from, type,
  direction)` removes every one of a type. Neither deletes a node.

### `update`

`update` loads the object, applies the change, and writes what the change altered: the fields that
differ, a field the change set to null, and for a view the relationships it added or dropped,
nested views included. A relationship another writer added in the meantime is kept. On a conflict it
loads again and re-applies the change, three times by default.

### From Java

```java
stateless.save(view);
stateless.save(view, Replace.of(Set.of("mentions")));
stateless.saveFields(person, Add.INSTANCE, NullPolicy.IGNORE, Set.of("name"));
stateless.update(id, Person.class, p -> p.withName("Ada"));
```

## `@NodeStamp`

```kotlin
@NodeFragment(labels = ["Person"])
data class Person(
    @NodeId val id: String,
    val name: String,
    @NodeStamp val stamp: String? = null,
)
```

The field is optional and strongly recommended: without it a save is never checked.

- The stamp is stored on the node under `__drivine.stamp`, whatever the field is called. Loading
  fills the field.
- A save that changes a node writes a new stamp: a property that differs, a cleared property that
  held a value, a label added or dropped, or a node with no stamp yet. A save that changes nothing
  leaves the stamp as it is. The save statement makes the comparison, so there is no extra read.
- A stateless save of an object that carries a stamp applies only if the node still has it.
  Otherwise nothing is written and `StaleObjectException` says whether the node changed or was
  deleted. The check is part of the save statement: one round trip, and atomic on an engine without
  transactions.
- A save of an object whose stamp is null is not checked. It creates the node or overwrites it.
- `save` returns the object with the stamp the node is left with. Use the returned object.
- In a view, the root is checked. A node reached through a relationship is written unchecked, and
  keeps its stamp unless the save changes one of its properties.
- Adding or removing a relationship changes no node's stamp.
- `saveAll` and `GraphObjectManager` stamp the nodes they change and check none.

### Cypher you write yourself

Cypher that changes a stamped node's mapped properties should give it a new stamp, or a checked save
will not notice the change:

```kotlin
"MATCH (p:Person {id: \$id}) SET p.name = \$name, ${Stamps.setClause("p")}"
```

A node that is deleted and created again is noticed without this, because it has no stamp.

### Cost

Measured against writing a stamp on every save, on Neo4j, FalkorDB and Memgraph: no measurable
difference on a single save, embeddings included, and at most about 4 microseconds a node in a
batch. The stamp takes 48 bytes a node.

## `@ReadOnly`

A view field that is loaded and never written.

```kotlin
@ReadOnly @GraphRelationship(type = "REVIEWED_BY")
val reviewers: List<Person>

@ReadOnly @GraphPath([Hop("MENTIONS", OUTGOING, label = "Person"), Hop("WORKS_AT", OUTGOING)])
val employers: List<Organization>
```

- Every save skips it, on both managers: no relationship is written and the nodes it holds are not
  saved.
- Naming it in `Replace` is an error, and `Replace.all()` leaves it alone.
- It is a choice on a `@GraphRelationship` field, and required on `@GraphPath`, `@Count` and
  `@Aggregate`.
- To write along a path: `edges.relate`, Cypher, or a view rooted where the hop starts.

## Moving from `GraphObjectManager`

| With `GraphObjectManager` | With `StatelessGraphObjectManager` |
|---|---|
| `save(obj)` of a new object | `save(obj)` |
| load, change a field, `save` | `update(id) { it.copy(...) }`, or `save` of the loaded object |
| load, drop an item from a list, `save` | `update(id) { ... }`, or `save(obj, Replace(View::field))` |
| `save(obj, CascadeType.DELETE_ORPHAN)` | `save(obj, Replace(View::field, removedTargets = DELETE_UNREFERENCED))` |
| `save(obj, CascadeType.PRESERVE)` | `save(obj)` |
| `save(obj, CascadeType.DELETE_ALL)` | no equivalent: delete the nodes with `delete` or Cypher |

- `DELETE_UNREFERENCED` deletes a removed target that no relationship points at. `DELETE_ORPHAN`
  deletes one with no relationship in either direction.
- Every test of `GraphObjectManager` in this repository has a mirror that runs on the stateless
  manager, and a comparison test runs the same scenarios through both and compares the graphs.

## Engines

Everything here is verified on Neo4j, FalkorDB and Memgraph. `CascadeType.DELETE_ORPHAN` on
`GraphObjectManager` remains unavailable on Memgraph; `DELETE_UNREFERENCED` is available there.
