# 0.0.79 — `searchK`: widening the vector search without widening the result

`k` handed to a vector index is the **HNSW search beam width**, not merely a row count. `searchK` lets a
caller widen the search and still get back the number of rows they asked for.

## The evidence

On a ~9K-vector index (1536-dim, cosine), after bulk-ingesting ~2K tightly-clustered vectors: a vector
verified as true global rank 3 — by exhaustive `vector.similarity.cosine` — was **not returned at any
k ≤ 100**, and came back at rank 3 at **k = 200**. Reproduced across two full index rebuilds, with
quantization on and off, and across a database restart.

That result proves the mechanism rather than suggesting it. If `k` only limited rows, a vector at true
rank 3 would appear at k = 100 — it is comfortably inside 100. The only way k = 200 finds it and k = 100
does not is if `k` drives the candidate queue. In Lucene-backed HNSW the result queue *is* the candidate
queue, so `ef_search == k`, and Neo4j exposes no separate knob.

Two consequences:

- **Raising `k` is the only query-time lever on recall.** An "over-fetch multiplier" and "an
  effective-k knob" are therefore the same lever, not two options.
- **Under-recall here is a tunable tradeoff, not a defect.** Dense clusters saturate every neighbour
  list: with `M = 16`, near-duplicate vectors consume all sixteen links with intra-cluster neighbours,
  pruning the long-range links greedy descent needs to enter or leave the cluster. Low `ef` cannot then
  recover. Raising `hnswM` / `hnswEfConstruction` attacks that cause directly — see
  [0.0.79-vector-index-tuning.md](0.0.79-vector-index-tuning.md).

## The compounding problem: post-filter dilution

`where {}` predicates apply **after** the index yields, so a scoped caller receives roughly
`k × selectivity` rows. At 22% selectivity, asking for 40 returns about **9** — and those survivors are
the intersection of "globally nearest" with "in scope", which is not "nearest within scope".

## Usage

```kotlin
// search with a beam of 200; return the best 40 that survive the filter
graphObjectManager.loadNearest<PropositionView>(dsl, queryVector, topK = 40, searchK = 200) {
    where { proposition.contextId eq ctx }
}
```

`searchK` is what the **index** is asked for. `topK` becomes a post-filter `LIMIT`.

This is the familiar fetch-200-trim-40 workaround, with the trim in the correct place: **after** the
`WHERE`. Trimming before the filter would discard exactly the rows over-fetching was meant to recover.

Emitted shape:

```cypher
CALL db.index.vector.queryNodes('Proposition_embedding_vector', $_vectorTopK, $_vectorQuery)
YIELD node, score
WITH node AS n, score AS _score
WHERE n.contextId = $p0
RETURN { value: {…}, score: _score } AS row
ORDER BY _score DESC
LIMIT $_vectorRowLimit
```

with `_vectorTopK = 200` and `_vectorRowLimit = 40`.

## Over-fetching re-ranks (Neo4j)

Widening the beam only pays off if the trim that follows re-ranks by **exact** similarity. When
`searchK` is set, the Neo4j head yields `node` alone and recomputes the score with the index's own
similarity function:

```cypher
CALL db.index.vector.queryNodes('Doc_embedding_vector', $_vectorTopK, $_vectorQuery)
YIELD node
WITH node AS doc, vector.similarity.cosine(node.embedding, $_vectorQuery) AS _score
```

Because the index's yielded score is **approximate**. Neo4j 2026.04 enables
`vector.quantization.enabled` by default, so the score is computed against quantized vectors. The
effect is measurable on a four-dimensional toy vector: a node whose exact normalized cosine is 0.8 is
reported by the index as 0.7998811. Pin quantization off and the same index reports exactly 0.8 —
which is the causal chain, verified end to end in `VectorSearchNeo4jTest`.

A beam ordered by that approximate score therefore does not reproduce exact-similarity order, and a
trailing `LIMIT` over it discards true matches the beam already found. Measured on a 9k-vector,
1536-dim cosine index with one dense cluster: the true top 40 were all present inside a beam of 200,
yet trimming by the yielded score returned only 38 — recall 0.95. Re-ranking the same beam returned all
40.

So the rescore is the load-bearing half of `searchK`: without it, over-fetching buys row *count* on the
filtered path but not row *correctness*.

Two consequences to know:

- **Scores differ slightly between a tuned and an untuned call** for the same node — approximate versus
  exact. Verified to be the same normalization, not merely the same ballpark, so `threshold` keeps its
  meaning in general.

  **The exception matters if your threshold is a round number.** A node whose true similarity is exactly
  0.8 is reported by the index as 0.7998811, so `threshold = 0.8` *excludes* it without `searchK` and
  *includes* it with. Any node whose true similarity lies within roughly 1e-4 of the threshold can flip.
  A threshold of exactly 0.8 is a common default, so this is worth knowing before attributing the
  difference to recall.

  The gating is the reason: the exact re-rank is tied to `rowLimitParam`, i.e. to `searchK`, but the
  *cause* of the approximation is quantization, not over-fetching. So exact scores currently cannot be
  had without also paying for a wider beam. Decoupling them — always re-ranking on Neo4j, or a separate
  opt-in — is a live design question; it would cost a property read per row on every vector query and
  would end the byte-identical-when-off guarantee.
- **Neo4j only.** FalkorDB and Memgraph over-fetch and trim by their own engine score. `searchK` still
  widens the beam and still recovers rows on the filtered path there; it does not re-rank.

## Properties worth knowing

- **Off by default is a genuine no-op.** Omit `searchK` and the emitted Cypher is byte-identical to what
  an untuned search has always produced — no stray `LIMIT`, no extra binding. Pinned by a test, because
  "we added a knob and every existing query changed shape" is its own risk.
- **`searchK < topK` throws.** It would ask the index for fewer rows than the caller wants back, which
  can only lose results — a mistake rather than a tuning choice.
- **Available everywhere the search is.** Manager API, reified extensions, and the codegen'd per-view
  wrapper — a filtered view search is the case that needs it most, and a knob unreachable from the
  generated extension is not a knob.

## Seeing a diluted result

A short result is otherwise silent — the caller gets a short list and cannot tell dilution from a
genuinely small result. A vector search returning fewer rows than requested now logs, at DEBUG:

```
Vector search on PropositionView returned 9 of 40 requested rows; the index was asked for 200.
Filters apply after the index yields, so a scoped search thins the result — raise searchK to
widen the search, or search a partition's own index.
```

Turn up `org.drivine.manager.GraphObjectManager` when recall looks wrong.

**DEBUG rather than WARN, deliberately.** A view with required relationships routinely returns fewer
than `topK` — documented, intended behaviour — so warning would be noise that teaches people to ignore
the warning. Gating it behind a "shortfall greater than X" heuristic would mean picking X from a
selectivity estimate Drivine does not have.

One number is deliberately absent: how many rows the index yielded **before** the filter. Observing it
means restructuring the query to aggregate pre-filter, changing the plan shape and costing every caller
on every query — and it is redundant in the only case that matters. When the result is short of `topK`
the trailing `LIMIT` never bound, so the rows returned *are* the post-filter survivors.

## What Drivine deliberately does not do

No automatic over-fetch multiplier, no adaptive top-up loop that retries with a larger `k`, no
exact-scan fallback threshold. Each would have Drivine choosing a cost/correctness tradeoff from a
selectivity estimate it does not have — the same rule that stops it substituting its own HNSW defaults.
The knob is explicit; the policy is the caller's.

## If recall is poor, in order

1. **Measure.** Exhaustive `vector.similarity.cosine` for ground truth, then compare against the ANN
   result at a range of `k`. Everything else is guesswork without this.
2. **Raise `searchK`.** Free to try, no rebuild.
3. **Raise `hnswM` / `hnswEfConstruction`** and rebuild — attacks the cluster-navigation cause rather
   than the symptom, at the cost of index size and build time.

Steps 2–3 address under-recall. They do **not** address dilution: even with perfect recall, a `k` of 40
over a whole index filtered to one scope still yields about `40 × selectivity` rows.

## Tests

`query/VectorSearchKTest` — the binding, the post-filter `LIMIT` position, and that omitting `searchK`
changes nothing. `query/grammar/VectorSearchGrammarTest` — the re-ranked head for both similarity
functions, and the byte-identical untuned head. `manager/VectorSearchNeo4jTest` — against a live
engine: the rescore is on the index's scale, the index score is measurably approximate, and pinning
quantization off makes it exact. `query/VectorYieldReportingTest` — the counts a plan carries so a short result is
interpretable. `sample/GeneratedLoadNearestTest` pins that it reaches the generated extension.
