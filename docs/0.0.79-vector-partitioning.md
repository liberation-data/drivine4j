# 0.0.79 — `partitionLabel`: targeting a vector index at runtime

Previously the index a vector read searched was a **compile-time** function of the fragment:
`VectorIndexResolver` derived the label from `FragmentModel.labelsFor(fragmentClass)`, and the index
name derived from that. One vector index per partition — per corpus, tenant, or any other scope — needs
it to be a **runtime** function of the query, and nothing a caller could do reached below that.

## Why partition at all

`where {}` predicates apply **after** the index yields, so a scoped caller receives roughly
`k × selectivity` rows. At 22% selectivity, asking for 40 returns about 9 — and those survivors are the
intersection of "globally nearest" with "in scope", which is not "nearest within scope".

[`searchK`](0.0.79-vector-search-k.md) mitigates that by searching wider. A per-partition index removes
it: the ANN search runs **inside** the partition, pre-filtered by construction, so `k` recovers its
intuitive meaning and every returned row already belongs to the scope.

The two fix different problems. Even with perfect HNSW recall, a `k` of 40 over a whole index filtered
to one scope still yields about `40 × selectivity` rows.

## Usage

Create the per-partition index — nothing new is needed, the imperative API already accepts an arbitrary
label at runtime:

```kotlin
persistenceManager.indexes.ensure(VectorIndexSpec("Corpus_abc", "embedding", 1536))
```

Then name the partition on the read:

```kotlin
graphObjectManager.loadNearest(
    PropositionNode::class.java, null, queryVector,
    topK = 40, threshold = null, searchK = null, partitionLabel = "Corpus_abc",
)
```

Nodes carry both labels — `:Proposition:Corpus_abc` — so a node is stored once and indexed in both the
label-wide index and its partition's. Overlapping membership is free: a node in two partitions carries
both labels.

Composes with `searchK`: search wide *inside* a partition, then trim.

## Three properties that matter

**Targeting is not identity.** `partitionLabel` changes only which index is *located*. The yielded node
still carries the fragment's own label, so `where {}` and the projection are untouched, and
`:Proposition:Corpus_abc` projects as a `Proposition`. A test asserts the projection is byte-identical
with and without a partition, because the whole scheme rests on it.

**The label is the parameter, not the index name.** The name re-derives as
`${label}_${property}_vector`, which is exactly `VectorIndexSpec.defaultName()`. Letting callers pass a
name directly would break the create/read symmetry — the same symmetry the blank-index-name fix in
0.0.78 had to repair. Consequence: a fragment whose `@VectorIndex` pins an explicit name **cannot** be
partitioned, and throws saying so rather than quietly searching the wrong index.

**It is bound, not interpolated.** A literal would compile a distinct query string per partition, so the
plan cache would hold one plan per corpus instead of one in total, and a label derived from application
data would be concatenated straight into Cypher. Neo4j and Memgraph accept the bound form for the index
name; FalkorDB accepts it for the label it addresses indexes by. All three are verified end-to-end,
each asserting that **only the partition's members come back** — not merely that the query ran, which
is worthless evidence on FalkorDB given it silently accepts nonsense.

## Where the policy lives

Drivine targets the index it is told to target. It does not decide which corpora get their own index,
how large a partition must be to deserve one, or when to fall back to an exhaustive scan — those need a
selectivity estimate it does not have, and the same rule stops it substituting its own HNSW defaults.

A workable layout, for the consumer to own:

| Partition size | Physical layout | Read |
|---|---|---|
| small | shared bucket label | exhaustive `vector.similarity.cosine`, exact |
| medium | shared bucket label | ANN on the bucket, post-filter (dilution bounded by bucket size) |
| large | dedicated label | ANN on its own index, pre-filtered |

That gives a bounded number of HNSW graphs with an unbounded number of logical partitions, which is what
breaks under naive one-label-per-partition-forever. Note that only a **label** makes the routing
decision free: `MATCH (n:Corpus_abc) RETURN count(n)` is count-store metadata, O(1), while the same check
against a property is an index scan.

Creating a partition's index is a schema operation, and Neo4j rejects schema DDL inside an open data
transaction — so do it at ingest, not per request. Ingest is already doing chunking, embedding and bulk
insert, so it is a natural place for a schema event.

## A coupling `partitionLabel` breaks

A vector search never re-`MATCH`es the fragment's label — it projects whatever the index `CALL` yields.
That is safe by construction *without* a partition: the index name derives from the fragment's own
label, so membership of the index implies membership of the label.

`partitionLabel` breaks that coupling. If a partition index ever covers nodes of more than one fragment
type — the shared-bucket tier above is where that would happen — the search will project them as the
searched fragment. Keep a bucket homogeneous, or add a label guard in the caller.

A guard inside Drivine would run *after* the index yields, so it would convert silent mis-projection
into visible under-delivery (which the short-read reporting then surfaces) rather than making a
heterogeneous bucket work. If added, it should be gated on `partitionLabel != null` so unpartitioned
reads stay byte-identical.

## Not yet supported

**Cross-partition search.** `partitionLabel` targets one partition. Searching several needs one call per
index, merged and re-ranked, which changes what `k` means (k per index, then a global top-k). Deferred
as its own design.
