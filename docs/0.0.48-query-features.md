# Query features in 0.0.48

Maintainer handoff for the two `GraphObjectManager` query features added in 0.0.48:
1. **Quantified predicates** (`any{}` / `none{}`) over a to-many `@GraphRelationship` in `where{}`.
2. **Filtered vector search** — caller `where{}` predicates AND-ed into `loadNearest`.

Both are verified end-to-end against Neo4j, FalkorDB, and Memgraph.

---

## Feature 1 — `any{}` / `none{}` over a to-many relationship

```kotlin
loadAll<PropositionView> { where { mentions.any { resolvedId eq entityId } } }
loadAll<PropositionView> { where { mentions.any { resolvedId inList entityIds } } }
loadAll<PropositionView> { where { mentions.none { resolvedId eq entityId } } }
loadAll<PropositionView> { where { mentions.any { role eq "SUBJECT"; resolvedId eq entityId } } } // correlated
```

### Design decisions (and what diverged from the original spec)

- **No codegen change.** The spec assumed the KSP codegen would need to emit a quantifier accessor
  for `List<>` relationships. It doesn't: codegen already emits a to-many relationship as the target
  `Properties` object (e.g. `MentionProperties("mentions")`, alias = the relationship field name),
  identical to a to-one. So `any`/`none` are **pure runtime context-extensions on `NodeReference`**
  (`GraphQueryDsl.kt`) — the receiver is the target `Properties`, so the target's fields are in scope
  inside the block. Lower-risk, and works for any generated or hand-written DSL.
- **`any{}` is the explicit form of the existing flat shorthand.** `mentions.resolvedId eq id`
  already worked: `CypherGenerator.groupConditionsByAlias` converts a property condition whose alias
  is a relationship name into a `RelationshipCondition`, rendered via `grammar.filteredExistenceCheck`.
  `any{}` builds the same condition; the block just makes per-element correlation explicit and gives
  a home to `none{}`.
- **`none{}` = `negate` flag + portable `NOT (...)`.** Added `negate: Boolean` to
  `WhereCondition.RelationshipCondition`; `CypherGenerator.buildRelationshipCondition` wraps the
  positive inline condition in `NOT (...)` at every return site. This is portable across engines —
  no new per-grammar method — because the positive form is already engine-correct.
- **Reuses the existing per-grammar existence rendering** (`filteredExistenceCheck`), which already
  varies by engine and is battle-tested by the relationship-filter DSL.

### Generated Cypher (per engine), `mentions.any { resolvedId eq $id }`

| Engine   | Rendering |
|----------|-----------|
| Neo4j 5  | `EXISTS { (proposition)-[:HAS_MENTION]->(mentions) WHERE mentions.resolvedId = $id }` |
| Memgraph | `size([(proposition)-[:HAS_MENTION]->(mentions) WHERE mentions.resolvedId = $id | 1]) > 0` |
| FalkorDB | `CALL { WITH proposition OPTIONAL MATCH (proposition)-[:HAS_MENTION]->(mentions) WHERE … RETURN count(mentions) AS _ec0 }` → `_ec0 > 0` |
| Neptune  | inherits openCypher (CALL-subquery form); engines without subquery support throw per the grammar default |

`none{}` wraps the above in `NOT (...)`.

### Code

- `query/dsl/GraphQueryDsl.kt` — `RelationshipCondition.negate`; `any`/`none` context-extensions.
- `query/dsl/PropertyReference.kt` — `inList` infix (readable alias for the backtick `` `in` ``).
- `query/dsl/CypherGenerator.kt` — `finalize()` NOT-wrapping at the relationship-condition returns.

## Feature 2 — filtered vector search: `loadNearest(..) { where { } }`

```kotlin
loadNearest(PropositionView::class.java, queryObject, queryVector, topK = 20) {
    where { query.proposition.contextId eq ctx; query.proposition.status eq "active" }
}
```

### Design decisions

- **Property predicates only, on the projected root — by construction.** The vector path filters
  *after* projection, where the root has been rebound to a map (`proposition {…} AS proposition`).
  Property predicates render as `proposition.contextId = $p` (map-key access) and AND straight into
  the existing post-projection `WHERE` — **byte-identical to the load path's predicate rendering**,
  reusing `CypherGenerator.buildWhereClause`. This is also why the documented FalkorDB
  vecf32-Pointer quirk isn't re-triggered: the filter is a scalar on a map, not a pattern on the node.
- **Relationship-quantifier predicates are rejected here (for now).** They render as
  `EXISTS { (proposition)-[…] }`, which can't traverse a map. The manager detects any
  relationship predicate (`hasRelationshipPredicate`) and throws `UnsupportedOperationException`
  with a clear message rather than emitting broken Cypher. See follow-ups.
- **`topK` semantics unchanged** — it's the index's `k`; post-filtering may yield fewer rows.
- Shared execution: both `loadNearest` paths funnel through `executeVectorSearch(...)`
  (rows → `Scored<T>` + snapshot).

### Generated Cypher (Neo4j) — vector + property predicate

```cypher
CALL db.index.vector.queryNodes('Proposition_embedding_vector', $_vectorTopK, $_vectorQuery)
YIELD node, score
WITH node AS proposition, score AS _score
WITH proposition { … } AS proposition, [(proposition)-[:HAS_MENTION]->(mentions) | …] AS mentions, _score
WHERE proposition.contextId = $param_proposition_contextId_0
  AND proposition.status = $param_proposition_status_1
RETURN { value: { proposition: proposition, mentions: mentions }, score: _score } AS row
ORDER BY _score DESC
```

(FalkorDB/Memgraph differ only in the vector head; the property `WHERE` is identical.)

### Code

- `query/GraphViewVectorSearchBuilder.kt` — `build(..., callerWhere)`: ANDs the caller clause into
  the post-projection filter.
- `query/GraphViewQueryBuilder.kt` — `buildVectorQuery(.., callerWhere)`.
- `manager/GraphObjectManager.kt` — `loadNearest(graphClass, queryObject, vector, topK, threshold, spec)`
  overload; renders caller conditions, guards relationship predicates, merges bindings;
  `executeVectorSearch(...)` helper; `hasRelationshipPredicate(...)`.

## Tests

- `query/dsl/QuantifiedRelationshipTest` — DSL builds the right condition; per-grammar rendering
  (Neo4j `EXISTS`/`NOT EXISTS`, Memgraph `size([…])>0`/negation).
- `manager/QuantifiedRelationshipCrossEngineTest` — `any`/`none` correct rows on all three engines,
  including correlation (one element satisfying several conditions) and `none` matching
  no-relationship roots.
- `query/VectorSearchBuilderTest` — caller `WHERE` ANDs into the post-projection filter.
- `manager/FilteredVectorSearchCrossEngineTest` — vector + property predicate on all three engines;
  proves the predicate genuinely prunes (joint-nearest nodes failing it are excluded, a far node
  matching it is included), and that a relationship predicate throws.

## Follow-ups

1. **`allEntityIds` "all present" combinator** — `all(x IN $ids WHERE EXISTS { (root)-[:HAS_MENTION]->(m) WHERE m.resolvedId = x })`.
   Deferred; `any`/`none` shipped first as the spec allowed.
2. **Relationship-quantifier predicates inside `loadNearest { where { } }`** — would need rendering
   pre-projection (on the raw node) and re-verifying the FalkorDB `vecf32`-Pointer behaviour for the
   `filteredExistenceCheck` CALL/size forms. Currently throws.
3. **Codegen `loadNearest { }` extension** — ✅ **done in 0.0.54.** The codegen now emits a reified
   `loadNearest(vector, topK, threshold) { where { } }` per `@VectorIndex`-ed view (mirrors the
   generated `loadAll { }`), so callers don't pass the query object. See `docs/codegen-loadnearest-0.0.54.md`.
4. **Out of scope (per spec):** the self-similarity / all-pairs "cluster" primitive stays as
   consumer-local Cypher.
