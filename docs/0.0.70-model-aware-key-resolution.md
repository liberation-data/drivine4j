# Model-aware key resolution — `field(key)` / `predicateOn(key, …)` — 0.0.70

Follow-up to the dynamic-predicate path (0.0.69). `property(path)` / `predicate(path, op, value)` take a
**stored** property name, which pushes the *logical-key → stored-path* mapping onto the caller. This adds
a resolving pair — `field(key)` / `predicateOn(key, op, value)` — that consults a mapping the generated
`<Fragment>QueryDsl` now carries, derived from the fragment's own `@GraphProperty` / `@PropertyBag`
annotations. The consumer stops re-encoding its model's structure.

```kotlin
// 0.0.69 — consumer owns the split:
where { query.predicate(if (key in STRUCTURAL_KEYS) key else "metadata.$key", op, value) }

// 0.0.70 — the QueryDsl already has the metadata:
where { query.field("containerSectionId") eq "s1" }   // @GraphProperty  → n.container_section_id
where { query.field("source") eq "wiki" }              // @PropertyBag    → n.`metadata.source`
where { query.predicateOn(key, op, value) }            // resolving, programmatic
```

## The interface

`ResolvableNodeReference : NodeReference` (`org.drivine.query.dsl`) carries the resolver:

```kotlin
interface ResolvableNodeReference : NodeReference {
    val fieldKeyPaths: Map<String, String>   // logical key (Kotlin name AND @GraphProperty on-disk name) → stored name
    val bagPrefixes: List<String>            // @PropertyBag stored prefixes (incl. delimiter), one per bag
}
```

Every generated `<Fragment>QueryDsl` now implements it (previously `NodeReference`). Because
`ResolvableNodeReference` extends `NodeReference`, this is source-compatible — all existing DSL usage
keeps working.

## Resolution rules (`resolveKey`)

Given a logical `key`:

1. **Declared field** — `fieldKeyPaths[key]` (populated with both the Kotlin/Java name *and* the
   `@GraphProperty` on-disk name, each → the on-disk name). `containerSectionId` and `container_section_id`
   both → `container_section_id`, rendering `n.container_section_id`.
2. **`@PropertyBag` key** — unmatched key + exactly one bag → `` `<prefix>key` `` (dotted, backtick-quoted
   by `CypherGenerator`). `source` → `` n.`metadata.source` ``.
3. **Unresolvable** — unmatched key with **zero** bags (no such field) or **more than one** bag
   (ambiguous) → throws `IllegalArgumentException` at build time with a clear message. Never guesses.

`field(key)` is the resolving counterpart of `property` (returns `PropertyReference<Any?>`, base
operators); `predicateOn(key, op, value)` is the resolving counterpart of `predicate` (full
`ComparisonOperator` set). The stored-path `property`/`predicate` remain for callers that already have an
on-disk path — this is additive.

## Codegen

Both generators tap the exact point where the Kotlin/Java name and the computed on-disk name /
`@PropertyBag` prefix are already in scope (they're what the typed accessors are built from), and
accumulate the resolver as each reference is emitted:

- **KSP** (`drivine4j-codegen`): `generateFragmentDslClass` implements `ResolvableNodeReference`;
  `addPropertyReference` returns an `EmittedRef` (`Field(logicalName, onDiskName)` / `Bag(storedPrefix)`)
  that the loop folds into `fieldKeyPaths` + `bagPrefixes`, emitted as `override val` initializers.
- **APT** (`drivine4j-codegen-java`): `addPropertyGetters` gains optional out-collections it populates;
  `generateFragmentDsl` implements `ResolvableNodeReference` and emits `getFieldKeyPaths()` /
  `getBagPrefixes()` (a `LinkedHashMap`/`ArrayList` builder, or `Collections.empty*()`). The view
  `Properties` caller passes `null, null` (no resolver).

The `@PropertyBag` *field name* is deliberately **not** a `fieldKeyPaths` entry — free-form keys are
reached through the prefix, not by the bag field's own name.

## Tests

- `query/dsl/KeyResolutionTest` (unit) — resolve by Kotlin name and on-disk name; unmatched → single bag
  prefix; **throws** for zero bags and for multiple bags; `field()`/`predicateOn()` render the resolved
  stored path (bag key backtick-quoted).
- `drivine4j-sample/GeneratedKeyResolverTest` (KSP) — a mixed `@GraphProperty` + `@PropertyBag` fragment
  (`SampleResolverNode`) generates `: ResolvableNodeReference` with `"sectionId" to "section_id"`,
  `"section_id" to "section_id"`, and `bagPrefixes = listOf("metadata.")`; the bag field is not a key.
- `drivine4j-codegen-java/PropertyBagCodegenTest#emitsModelAwareKeyResolverForMixedFragment` (APT) — the
  Java-generated DSL implements `ResolvableNodeReference` and emits the two getters with the same maps.
- `manager/DynamicPropertyFilterCrossEngineTest` (Neo4j / FalkorDB / Memgraph) — `field("sectionId")` and
  `field("section_id")` both hit `section_id`; a free-form `field("source")` hits `metadata.source` and
  matches the explicit `property("metadata.source")` form; `predicateOn` resolves identically.

## Consumer impact (`embabel-agent-rag-graph`)

Deletes `ChunkNode.STRUCTURAL_KEYS` + `storedPathFor` and the `pathFor` bridge in the `PropertyFilter →
where { }` translator: each `predicate(pathFor(f.key), …)` becomes `predicateOn(f.key, …)`. The translator
stops knowing the model's structure — drivine resolves it from the `@GraphProperty` / `@PropertyBag`
annotations that are the single source of truth.

## Follow-ups

1. **Java-friendly `field` / `predicateOn`** — `PropertyConditionBuilder`-returning variants for the Java
   fluent path (this bump is Kotlin-context-parameter only).
2. **View-level resolution** — resolution is per-fragment; a `@GraphView`'s aggregate DSL resolves via
   its root reference (`query.<root>.field(key)`), which is itself resolvable.
