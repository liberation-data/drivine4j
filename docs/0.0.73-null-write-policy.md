# Null-write policy — `NullPolicy` (IGNORE default) — 0.0.73

Maintainer handoff for making null-on-save a **single declared contract** instead of behaviour that was
emergent from implementation details. Previously "does a null field clear the stored property?" depended
on four hidden axes — single `save` vs `saveAll`, bagged vs bagless fragment, a vector-wrapping engine
(FalkorDB) vs not, and tracked vs detached — so a caller couldn't reason about it from the call site.
The acute case: a null `@VectorIndex` embedding on a partially-loaded object silently wiped a computed
vector.

## The contract

One policy, defined purely on **the object you pass**, applied identically across single/batch,
bagged/bagless, and every engine:

```kotlin
gom.save(chunk)                              // IGNORE (default): merge-patch — nulls left untouched
gom.save(chunk, nullPolicy = NullPolicy.CLEAR)   // full overwrite — nulls clear the property
gom.saveAll(chunks)                          // IGNORE (default)
gom.saveAll(chunks, nullPolicy = NullPolicy.CLEAR)
```

- **`IGNORE` (default):** only non-null fields are written; nothing is ever cleared. A partially-loaded
  object never destroys stored data.
- **`CLEAR`:** the object is authoritative — null fields clear the corresponding property.

**No field is special.** An embedding is treated like any other property: preserved under `IGNORE`,
cleared under `CLEAR`. The protection against wiping a computed vector comes from the **default being
`IGNORE`**, not a per-field exception — so `save(chunk)` is safe by construction, and there's no
carve-out to remember or reason around. (A null embedding under `CLEAR` clears with a plain `SET x =
null`; we only wrap *non-null* values in `vecf32(...)`, so there's no invalid `vecf32(null)`.)

## The key design decision: null semantics are decoupled from dirty-tracking

The footgun's root was that the snapshot/dirty system *decided* whether a null was written. Now:

- **The policy decides nulls**, independent of any snapshot: `IGNORE` always skips a null, `CLEAR`
  always clears one. So the observable result never depends on tracked-vs-detached, and there's no
  merge-patch snapshot-drift ("save a null, snapshot records null, DB still has the value, next CLEAR
  mis-diffs") — because CLEAR never consults the snapshot for nulls.
- **Dirty-tracking is now only an optimization:** it may skip re-writing an unchanged **non-null**
  field (a true no-op). It never gates a null. This means `saveAll` did **not** need to be made
  dirty-aware for the contract to be consistent — its UNWIND path drops nulls under `IGNORE` and keeps
  them (so `+= {x: null}` clears) under `CLEAR`, matching single `save` observably.

## Behaviour changes (pre-1.0)

- **Single `save` default flipped `CLEAR` → `IGNORE`.** Saving an object with a null field no longer
  clears that property by default; pass `NullPolicy.CLEAR` to clear. (Non-null fields are unchanged;
  dirty-tracked partial updates behaved this way already — confirmed by `PersonRepositoryTests`.)
- **`saveAll` is now consistent with `save`** (previously it silently ignored nulls in the UNWIND path
  but cleared them in the bagged/vector fallback).
- **Stale `@PropertyBag` key `REMOVE`** now only happens under `CLEAR` (removal is a clear); under
  `IGNORE` orphaned keys are left (merge-patch).
- **Vector null no longer clears under the default** — the original footgun, fixed by the `IGNORE`
  default rather than a hardcoded skip.

## Code map

- `manager/NullPolicy.kt` — the enum + the contract doc.
- `manager/GraphObjectManager.save` / `saveAll` — `@JvmOverloads`, `nullPolicy` param defaulting to
  `IGNORE`. (No `merge`/`mergeAll` aliases — with an `IGNORE` default, `save` *is* the merge-patch; the
  explicit destructive form is `save(obj, NullPolicy.CLEAR)`.)
- `query/FragmentMergeBuilder` — scalar loop: nulls handled by policy only (CLEAR emits `SET x = null`,
  IGNORE skips), non-nulls dirty-optimized; vectors wrap only when non-null; bag null values + stale-key
  `REMOVE` gated on `CLEAR`.
- `query/GraphObjectMergeBuilder` / `GraphViewMergeBuilder` — `nullPolicy` threaded (default `IGNORE`);
  it governs the root fragment of a view (relationship-target writes stay merge-patch — a follow-up if
  per-relationship tuning is ever wanted).
- `manager/BatchSaveOperations` — `nullPolicy` threaded; `unwindRootRow` drops nulls under `IGNORE`,
  keeps them under `CLEAR` (`+= {x: null}` clears; verified on Neo4j/Memgraph); the per-item fallback
  delegates to `FragmentMergeBuilder` with the policy.

## Tests

- `query/NullPolicyMergeBuilderTest` (unit) — IGNORE skips null scalar+embedding; CLEAR clears both
  (embedding via plain `SET`, never `vecf32(null)`); non-null embedding wraps under either policy; bag
  null clears under CLEAR / skipped under IGNORE; default is IGNORE.
- `query/VectorMergeBuilderTest` — null embedding untouched by default, cleared (plain) under CLEAR.
- `manager/NullPolicyCrossEngineTest` (Neo4j / FalkorDB / Memgraph) — default `save`/`saveAll` never
  clear a null title or embedding; explicit `CLEAR` clears a null title (single: `SET`; batch:
  `+= {x:null}` on Neo4j/Memgraph, per-item on FalkorDB) and a null embedding.
- Regression: `PropertyBagMergeTest` stale-key tests opt into `CLEAR`; `SaveAllNeo4jTest`,
  `PersonRepositoryTests`, `GraphObjectManagerTests` all green under the new default.

## Consumer impact (`embabel-agent-rag-graph`)

The store's save path becomes safe **by default**: `gom.save(chunkNode)` (or `saveAll`) is a merge-patch
— a chunk reconstructed or loaded without its embedding will never wipe the stored vector, and no
special API is needed. Only reach for `NullPolicy.CLEAR` when you deliberately want a full overwrite
(e.g. genuinely nulling a field). The store can also drop any defensive load-merge it added purely to
dodge the old footgun. (Recommendation still stands to keep whatever load-merge is needed for *other*
reasons; this only removes the null-clobber hazard.)
