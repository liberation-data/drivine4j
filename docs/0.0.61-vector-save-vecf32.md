# Writing `@VectorIndex` properties as the engine's native vector type on save — 0.0.61

Maintainer handoff for the write-side vector fix: embeddings saved through `GraphObjectManager`
(`save` / `saveAll`) are now stored as the engine's native vector type, so FalkorDB's vector index
actually picks them up.

## The bug

Drivine wrapped the query vector in `vecf32(...)` on the **read** side for FalkorDB
(`FalkorDbCypherGrammar.vectorSearchHead`) but did nothing on the **write** side —
`FragmentMergeBuilder` rendered every property uniformly as `SET n.$field = $field`. On FalkorDB a
vector index only indexes a property stored as the native `Vectorf32` type; a plain array assigned to
that property is **silently accepted and silently left out of the index** (see the upstream report,
[FalkorDB#2233](https://github.com/FalkorDB/FalkorDB/issues/2233)). So saving an embedding through
`GraphObjectManager.save()` wrote a plain array, the index stayed empty, and `loadNearest` returned
nothing.

The asymmetry was masked because the existing cross-engine tests hand-wrote the literal in raw Cypher
(`VectorSearchCrossEngineTest`, `seed(pm) { "vecf32($it)" }`) rather than saving through the manager —
so `save()` → `loadNearest` on FalkorDB had no coverage at all.

Neo4j and Memgraph index a stored array directly and are unaffected; their write path stays
byte-identical.

## The fix — three seams, mirroring the read side

1. **Model awareness.** `FragmentField.vectorIndexed` marks a `@VectorIndex` field; `FragmentModel`
   populates it during field extraction (Kotlin + Java reflection, alongside how it already detects
   `@PropertyBag`) and exposes `FragmentModel.vectorFieldNames`.

2. **Write-side grammar hook.** `CypherGrammar.vectorPropertyLiteral(param): String` — default
   `"$param"` (plain bind), overridden to `"vecf32($param)"` in `FalkorDbCypherGrammar`. A derived
   `CypherGrammar.wrapsVectorLiteral` (true only when the literal wraps) gates the batch fallback with
   a single source of truth.

3. **Apply in the merge builder.** `FragmentMergeBuilder` branches the `SET` clause: a vector field
   with a non-null value is written as `n.$field = ${grammar.vectorPropertyLiteral(field)}`. **The
   binding is unchanged** — only the RHS differs. The grammar is threaded from `GraphObjectManager`
   (`persistenceManager.grammar`) through `GraphObjectMergeBuilder.forClass` → the fragment/view merge
   builders; it is nullable and defaults to plain output, so unit tests that construct the builder
   directly stay byte-identical.

### Null embeddings

`vecf32(null)` is invalid on FalkorDB, so a null vector value is **never wrapped** — it falls through
to a plain `SET n.$field = $field`, which clears the property, exactly matching normal null semantics.

### Batch path (`saveAll`)

The UNWIND batch upsert (`SET n += row.props`) cannot wrap one property in `vecf32(...)`. So a root
fragment carrying a `@VectorIndex` field **falls back to the per-item save path on engines that wrap**
(`grammar.wrapsVectorLiteral`, i.e. FalkorDB) — mirroring how a `@PropertyBag` root already falls
back. On Neo4j / Memgraph the UNWIND path is retained (a plain array indexes fine there), so batch
throughput is unchanged for them.

## Backend support

| Engine | Write form | Batch (`saveAll`) | Status |
|---|---|---|---|
| FalkorDB | `SET n.embedding = vecf32($embedding)` | per-item fallback (UNWIND can't wrap) | ✅ verified: save → indexed → `loadNearest` finds it |
| Neo4j | `SET n.embedding = $embedding` (unchanged) | UNWIND (unchanged) | ✅ verified, byte-identical write |
| Memgraph | `SET n.embedding = $embedding` (unchanged) | UNWIND (unchanged) | ✅ verified, byte-identical write |

## Read-back

A `vecf32`-stored property loads back through `FalkorDbResultMapper` as a plain `List` of numbers, so
`gom.load(...)` reconstructs the `List<Float>?` embedding field normally — covered by an explicit
round-trip assertion.

## Code map

- `CypherGrammar.vectorPropertyLiteral` / `wrapsVectorLiteral`; `FalkorDbCypherGrammar` override.
- `FragmentField.vectorIndexed`, `FragmentModel.vectorFieldNames` (+ Kotlin/Java detection).
- `FragmentMergeBuilder` — the `SET`-clause branch + null guard; nullable `grammar` param.
- `GraphObjectMergeBuilder.forClass`, `FragmentMergeBuilderAdapter`, `GraphViewMergeBuilder`
  (root + relationship-target fragment builders) — grammar threaded through.
- `BatchSaveOperations` — vector-bearing-root fallback gated on `wrapsVectorLiteral`; grammar threaded
  into the per-item merge builder.
- `GraphObjectManager` — passes `grammar` at the `save` and `saveAll` (`BatchSaveOperations`) sites.

## Tests

- `query/grammar/VectorSearchGrammarTest` — `vectorPropertyLiteral` / `wrapsVectorLiteral` per engine.
- `query/VectorMergeBuilderTest` — model recognizes the vector field; FalkorDB wraps (binding
  unchanged); Neo4j plain; null never wrapped; no-grammar plain.
- `manager/SaveThenVectorSearchCrossEngineTest` — **the actual gap**: saves through the manager
  (single `save`, view-root `save`, and batch `saveAll`) with no raw `vecf32` in the fixture, then
  `loadNearest` ranks/prunes and the embedding round-trips. Runs on FalkorDB (fails before the fix,
  passes after), plus Neo4j and Memgraph as regression guards.

### Test-hygiene notes (worth knowing)

Two non-obvious things surfaced writing the cross-engine test; neither is a product bug:

- **Session dirty-tracking vs. out-of-band delete.** A reused `GraphObjectManager` snapshots saved
  objects; if the graph is cleared with `DETACH DELETE` behind the session's back, the next `save` of
  the same object sees no dirty fields and skips the embedding write — leaving the index empty. The
  test builds a fresh manager per scenario (models a fresh process).
- **Memgraph vector index + delete.** Memgraph does not purge a `DETACH DELETE`d node from its HNSW
  vector index; a later search trips over it ("Trying to get labels from a deleted node") even after
  the index is recreated. The test avoids inter-scenario deletes, MERGE-ing stable ids instead. (A
  candidate upstream report if it recurs for the consumer.)

## Consumer migration note

`embabel-agent-rag-graph` can now persist embeddings via `save()` with a `@VectorIndex` property and
get working FalkorDB vector search — no need to hand-emit `vecf32(...)`. No API change; the fix is
transparent. The only behavioural change is on FalkorDB, and only in the correct direction (embeddings
now index instead of silently not indexing).

## Open follow-ups

1. **Relationship-fragment vectors** follow the same path (the view relationship-target builders are
   threaded), but aren't separately covered by a test.
2. If FalkorDB later errors or coerces on a non-`vecf32` write ([FalkorDB#2233](https://github.com/FalkorDB/FalkorDB/issues/2233)),
   the wrap stays correct and the silent-failure trap disappears.
