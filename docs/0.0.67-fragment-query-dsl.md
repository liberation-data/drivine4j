# Standalone query DSL for bare `@NodeFragment` — 0.0.67

Maintainer handoff for generating a type-safe query DSL for a **bare `@NodeFragment`**, not just for a
`@GraphView`. A fragment now gets a `<Fragment>QueryDsl` query object + `INSTANCE`, and (Kotlin) the
`INSTANCE`-injecting `loadAll` / `count` / `deleteAll` extensions bound to it — so you can query a node
type directly, with a `where` that targets its node properties.

```kotlin
// Kotlin — generated reified extensions
graphObjectManager.loadAll<ContentElementNode> { where { query.instanceOf<ChunkNode>() } }
graphObjectManager.count<Person> { where { query.name eq "Ada" } }
graphObjectManager.deleteAll(Chunk::class.java, ChunkQueryDsl.INSTANCE) { where { query.containerSectionId eq "sec-1" } }
```
```java
// Java — via the fluent builder
gom.query(Chunk.class).filterWith(ChunkQueryDsl.class).where(q -> q.containerSectionId().eq("sec-1")).loadAll();
```

## Using it — exact syntax and the trip-ups (read this first)

Copy these. Every snippet below compiles against the generated code; the ❌ ones are the mistakes
agents make most.

### Imports — you need `query`, and `instanceOf` only if you use it

```kotlin
import org.drivine.query.dsl.query          // the `query` receiver used inside where { }
import org.drivine.query.dsl.instanceOf     // ONLY if you call instanceOf<>()
import com.acme.model.DocumentNode          // the fragment
import com.acme.model.DocumentNodeQueryDsl  // its generated DSL (same package as the fragment)
```

- ❌ Do **not** import `where`, `eq`, `neq`, `and`, … — they are not top-level imports. `where { }` is a
  member of the query spec; `eq`/`neq`/`gt`/`contains`/`isNull`/… are infix operators resolved on the
  property reference *inside* `where { }`. Importing them fails; forgetting `import …dsl.query` is what
  makes `query` "unresolved".

### `query.<field>` uses the KOTLIN FIELD NAME — never the `@GraphProperty` on-disk name

```kotlin
// field: @GraphProperty("container_section_id") val containerSectionId: String?
where { query.containerSectionId eq "sec-1" }   // ✅ Kotlin field name
where { query.container_section_id eq "sec-1" } // ❌ does not compile — that's the on-disk name
```

The DSL maps the field to `container_section_id` in the emitted Cypher for you.

### Which form to use — this is the one agents get wrong

There are **two** call shapes. Pick by what you're filtering on:

**A. Query a concrete fragment (or a subtype) by ITS OWN properties → explicit 3-arg form.**

```kotlin
val docs = graphObjectManager.loadAll(
    DocumentNode::class.java,
    DocumentNodeQueryDsl.INSTANCE,
) {
    where { query.title eq "Intro" }        // any DocumentNode property
}
// count / deleteAll are the identical shape:
graphObjectManager.count(DocumentNode::class.java, DocumentNodeQueryDsl.INSTANCE) { where { query.title eq "Intro" } }
graphObjectManager.deleteAll(DocumentNode::class.java, DocumentNodeQueryDsl.INSTANCE) { where { query.title eq "Intro" } }
```

```kotlin
// ❌ For a SUBTYPE of a sealed fragment this does NOT give you the subtype's DSL:
graphObjectManager.loadAll<DocumentNode> { where { query.title eq "Intro" } }
//                        ^^^^^^^^^^^^                    ^^^^^^^^^^^
// `loadAll<Sub>` resolves to the sealed BASE's extension, whose `query` is the BASE DSL —
// so `query.title` (a DocumentNode-only property) won't resolve. Use form A above.
```

**B. Query a sealed/abstract base, optionally narrowing by type → reified `loadAll<Base> { }`.**

```kotlin
graphObjectManager.loadAll<ContentElementNode> {
    where {
        query.id eq theId                     // ✅ base properties only
        query.instanceOf<DocumentNode>()      // ✅ narrows to :Document; rows still deserialize to their concrete subtype
    }
}
```

You cannot mix: inside `loadAll<Base>`, `query` is the **base** DSL, so it exposes only base
properties. To filter by a subtype-specific property, use form **A** with that subtype's DSL.

> Rule of thumb: **filtering by a property the base doesn't have ⇒ explicit 3-arg form (A).**
> Everything else (base props, `instanceOf`, standalone non-sealed fragments) ⇒ reified `loadAll<T> { }`.

### Java

`query(...)` is a Kotlin extension on `GraphObjectManager`, so from Java call it statically on
`JavaQueryBuilderKt`:

```java
import org.drivine.query.dsl.JavaQueryBuilderKt;

List<DocumentNode> docs = JavaQueryBuilderKt
    .query(gom, DocumentNode.class)
    .filterWith(DocumentNodeQueryDsl.class)
    .where(q -> q.title().eq("Intro"))
    .loadAll();
```

- ❌ `gom.query(DocumentNode.class)` — no such member; it's an extension → `JavaQueryBuilderKt.query(gom, …)`.
- The property **accessor** depends on which codegen produced the DSL:
  - **Java APT** DSL → getter *method*: `q.title()`, `q.containerSectionId()`.
  - **Kotlin KSP** DSL used from Java → the `val` becomes a bean getter: `q.getTitle()`, `q.getContainerSectionId()`.
- Java has no reified generics and no ambiguity — always name the class + its `QueryDsl` explicitly.

## What it generates

Per `@NodeFragment`, a `<Fragment>QueryDsl` — a [`NodeReference`] at the fragment root alias `"n"`
(matching `FragmentQueryBuilder.nodeAlias`), exposing the node's property references (honoring
`@GraphProperty` on-disk names and `@PropertyBag`), an `INSTANCE`, and `instanceOf()` support for
sealed/abstract fragments. `where { query.<prop> … }` renders `n.<prop> …`; `instanceOf<Sub>()` renders
`n:<labels>`. Parameterized bindings (`$param_*`) — the same path the view DSL uses; no string splice.

**The runtime already supported this** — `loadAll(class, Q, spec)` / `count` / `deleteAll` route through
`GraphObjectQueryBuilder.forClass` → `FragmentQueryBuilder` (with `viewModel == null`), and the Java
`query(F).filterWith(FQueryDsl).…` fluent builder delegates to the same. This change is **codegen-only**:
the KSP and APT processors previously only visited `@GraphView`.

`loadNearest` for a `@VectorIndex` fragment needs no new codegen — the hand-written non-filtered reified
`loadNearest<T>(vector, topK, threshold)` already works for any `T`, fragments included.

## The sealed-hierarchy overload subtlety (Kotlin)

A reified `inline fun <reified T : Fragment> loadAll(spec)` is ambiguous for `loadAll<Sub>` when the
base also has one (a subtype satisfies `T : Base`, and neither candidate is more specific). So the
Kotlin generator emits the `loadAll`/`count`/`deleteAll` **extensions only for "root" fragments** — those
with no generated `@NodeFragment` supertype (sealed/abstract bases and standalone fragments). Every
fragment (including subtypes) still gets its **`QueryDsl` class**. Consequences:

- `loadAll<Base> { where { query.baseProp; query.instanceOf<Sub>() } }` — works (base extension).
- `loadAll<StandaloneFragment> { where { query.prop } }` — works.
- `loadAll<Sub> { }` — resolves to the base extension, typed `List<Sub>`, filterable on **base**
  properties.
- Filtering a subtype by its **own** property uses the explicit 3-arg form:
  `loadAll(Sub::class.java, SubQueryDsl.INSTANCE) { where { query.subProp eq … } }` — unambiguous, and
  the `SubQueryDsl` exists for exactly this.

Java has no extension functions, so **no ambiguity** — a `<F>QueryDsl` is generated for every fragment
and used explicitly via `query(F.class).filterWith(FQueryDsl.class)`.

## Backend support

The generated DSL is engine-agnostic (it feeds the same runtime); verified cross-engine
(Neo4j / FalkorDB / Memgraph) for `loadAll` / `count` / `deleteAll`, `where` (incl. a `@GraphProperty`
on-disk name), `instanceOf()` on a sealed base, and per-node polymorphic dispatch.

## Code map

- **Kotlin KSP** (`drivine4j-codegen`):
  - `GraphViewProcessor` — also collects `@NodeFragment` symbols; proceeds when there are fragments but
    no views.
  - `QueryDslGenerator` — `fragmentClasses` param; `generateFragmentDslFile` /
    `generateFragmentDslClass` / `fragmentDslExtension`; `emitExtensions` gated on
    `getAllSuperTypes()` not intersecting the fragment set (root-only extensions);
    `@Suppress("FINAL_UPPER_BOUND")` on the emitted extensions.
- **Java APT** (`drivine4j-codegen-java`):
  - `GraphViewProcessor` — `@SupportedAnnotationTypes` gains `NodeFragment`; collects and passes
    fragment classes.
  - `QueryDslGenerator` — `fragmentClasses`; `generateFragmentDsl`; the property-getter loop extracted
    into `addPropertyGetters(builder, fragment, aliasExpr)` (shared by `Properties` and the fragment
    DSL, alias via `$L`).

## Consumer impact

`embabel-agent-rag-graph` can query its promoted node types directly — e.g. all chunks in a section by
a `@GraphProperty` field, or a sealed `ContentElementNode` narrowed with `instanceOf()` — instead of a
hand-written `where`-string or a wrapping view. No runtime API change; the DSLs are additive generated
code.

## Follow-ups

1. **Filtered fragment `loadNearest`** — `loadNearest(F, FQueryDsl.INSTANCE, vector, topK) { where { } }`
   (vector search + a caller predicate on a bare fragment). The runtime `loadNearest(class, Q, spec)`
   currently requires a `@GraphView`; non-filtered fragment vector search already works.
2. **`loadAll<Sub>` ergonomics** — the subtype-explicit-form workaround is documented; a nicer typed
   entry for subtype-property filtering (without the base-extension overlap) would need a different DSL
   binding than reified upper bounds allow.
3. **`orderBy` / pagination context sugar** — the fragment DSL supports `where`; `orderBy` works through
   the same `GraphQuerySpec`, but the `query.<prop>`-style order sugar isn't separately covered here.
