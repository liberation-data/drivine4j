# Full-text search primitive — `loadMatching` — 0.0.68

Maintainer handoff for a first-class full-text **search** operation on `GraphObjectManager`, the exact
mirror of `loadNearest` (vector). Drivine already owned the full-text **index** (`@FullTextIndex` +
`FullTextIndexSpec` + per-engine DDL, 0.0.60); this adds the search side so consumers stop hand-writing
per-engine full-text Cypher and score normalization.

```kotlin
// Vector (already there)
gom.loadNearest<ChunkNode>(queryVector, topK = 20, threshold = 0.7): List<Scored<ChunkNode>>

// Full-text (new) — same shape
gom.loadMatching<ChunkNode>("graph databases", topK = 20): List<Scored<ChunkNode>>
```

`loadMatching` resolves the model's full-text index, runs the engine-appropriate query, and returns
**scored, typed, `[0, 1]`-normalized** results — cross-engine, no consumer Cypher, polymorphic dispatch
included.

## Using it — exact syntax and the trip-ups (read this first)

### Non-filtered — any `@NodeFragment` or `@GraphView`

```kotlin
import org.drivine.manager.loadMatching   // the reified extension

gom.loadMatching<ChunkNode>("graph databases", topK = 20)                    // fragment, returns List<Scored<ChunkNode>>
gom.loadMatching<ChunkNode>("graph databases", topK = 20, threshold = 0.5)   // drop hits below 0.5 normalized
gom.loadMatching<ContentElementNode>("graph", topK = 20)                     // sealed base → each hit typed to its subtype
gom.loadMatching<ChunkView>("graph", topK = 20)                             // view → projected view per hit
```

- `threshold` defaults to **`0.0`** (keep everything), not nullable like `loadNearest` — full-text
  scores are already normalized to `[0, 1]`, so `0.0` is the natural floor.
- `topK` is applied as a trailing **`LIMIT`** (the full-text `CALL` takes no `k`, unlike the vector
  index `CALL`). It is a hard cap on rows returned.

### Filtered — full-text **plus** a `where { }` predicate, one query

```kotlin
import org.drivine.query.dsl.query

// fragment (generated ChunkNodeQueryDsl):
gom.loadMatching<ChunkNode>("graph databases", topK = 20) {
    where { query.containerSectionId eq "sec-1" }
}
// explicit subtype/3-arg form (same rule as the 0.0.67 fragment DSL — a subtype's own property needs this):
gom.loadMatching(ChunkNode::class.java, ChunkNodeQueryDsl.INSTANCE, "graph databases", topK = 20) {
    where { query.containerSectionId eq "sec-1" }
}
```

- ❌ The filtered `loadMatching<Sub> { }` on a **subtype of a sealed fragment** binds to the base DSL —
  filter a subtype-only property with the explicit 3-arg form, exactly as [[fragment-query-dsl-0.0.67]]
  documents for `loadAll`.
- The generated filtered `loadMatching` extension is emitted **only** for `@FullTextIndex`-bearing
  views/fragments (the gate `loadNearest` uses for `@VectorIndex`). Import it from the fragment/view's
  package alongside the other generated extensions.

### Java — fluent `.match(...)`

```java
import org.drivine.manager.Scored;
import static org.drivine.query.dsl.JavaQueryBuilderKt.query;

List<Scored<ChunkNode>> hits = query(gom, ChunkNode.class)
    .filterWith(ChunkNodeQueryDsl.class)
    .where(q -> q.getContainerSectionId().eq("sec-1"))   // KSP DSL from Java → bean getter
    .match("graph databases", 20);
```

- `match(query, topK)` / `match(query, topK, threshold)` is the Java fluent form; it returns
  `List<Scored<T>>`. It works for both views and fragments.

### Query syntax & escaping

The `query` string is passed through to the engine's full-text query language (**Lucene** on Neo4j:
`AND` / `OR` / `"phrase"` / `field:term`; RediSearch on FalkorDB; Tantivy on Memgraph). Raw user input
is **not** escaped — if it may contain query-syntax metacharacters, wrap it (the naive `"\"$q\""`
phrase-wrap) or escape before calling. Honour `@FullTextIndex(analyzer = …)` at **index** time (it is
baked into the index; the search procedures take no query-time analyzer).

## 1. Annotation

`@FullTextIndex` already existed (0.0.60) and is unchanged — property-level (single-property) or
class-level (`@Repeatable`, multi-property via `properties`), with optional `name` / `analyzer`. There
is **no `group` attribute** (the original prompt suggested one); multi-property indexes are declared
class-level:

```kotlin
@NodeFragment(labels = ["Chunk"])
data class ChunkNode(@NodeId val id: String, @FullTextIndex val text: String, …)

@FullTextIndex(properties = ["name", "description"])   // one index spanning two fields
@NodeFragment(labels = ["Entity"])
data class EntityNode(@NodeId val id: String, val name: String, val description: String)
```

The same annotation drives schema `ensure` **and** search resolution — one source of truth, as
`@VectorIndex` is for vectors.

## 2. Runtime

`GraphObjectManager` gains (mirroring the `loadNearest` overloads):

- `loadMatching(class, query, topK, threshold = 0.0)` and `loadMatching(class, property?, query, topK, threshold)`
  — `@GraphView` searches its root fragment's index and returns the projected view; `@NodeFragment`
  searches and returns itself; `property` disambiguates when a fragment has several indexes.
- `loadMatching(class, Q, query, topK, threshold, spec)` — filtered, for **both** views and fragments.
- reified extensions in `GraphObjectManagerExtensions.kt`: `loadMatching<T>(query, topK, threshold)`,
  `loadMatching<T>(property?, …)`, `loadMatching<T, Q>(query, topK, threshold, spec)`.

Index resolution is a new `FullTextIndexResolver` (mirror of `VectorIndexResolver`): reads
`@FullTextIndex` (property- **and** class-level) off the root fragment, derives the index name
`${label}_${onDiskProperties joined by _}_fulltext` — matching `FullTextIndexSpec.defaultName()`, so the
searched name equals the created name on the name-keyed engines. `FullTextQuerySpec` carries `label`
(FalkorDB keys by label) + `indexName` (Neo4j/Memgraph key by name) + the bound param names.

Query builders `FragmentFullTextSearchBuilder` / `GraphViewFullTextSearchBuilder` mirror their vector
twins, adding the trailing `LIMIT $topK`. The filtered fragment form renders its `where` against the
node alias `n` (the same `FragmentQueryBuilder` alias the 0.0.67 DSL uses); the filtered view form
renders in projected-collection mode like filtered `loadNearest`.

**Architecture — planners + one executor.** Query construction lives in `ScoredSearchPlanner.kt`
(`org.drivine.query`): `VectorSearchPlanner` and `FullTextSearchPlanner`, each with `plan(...)`
(unfiltered) and `planFiltered(...)`, returning a `ScoredSearchPlan(cypher, bindings)`. They are pure
(grammar + inputs, no session/persistence) and own their bound-param names + support checks. The
manager keeps only thin public overloads that build the `GraphQuerySpec`, call a planner, and hand the
plan to one shared private `executeScoredSearch(graphClass, plan)` — which registers subtypes,
transforms each `{ value, score } AS row` with the same `TransformPostProcessor` `loadAll` uses, and
snapshots for dirty tracking. Both search kinds (and both filter forms) funnel through that one
executor, so `loadNearest` and `loadMatching` stay a few lines each and the manager stopped growing.

## 3. Score normalization (centralized — this bit the consumers)

Raw full-text scores are unbounded (Lucene) and not comparable across engines, and FalkorDB can yield
`0/0 = NaN`. Every grammar's `fullTextSearchHead` routes its `CALL` through one shared helper,
`CypherGrammar.normalizedFullTextHead`, which is **identical across engines**:

```cypher
<engine CALL … YIELD node, score>
WITH collect({node: node, score: score}) AS _ftResults, max(score) AS _ftMax
UNWIND _ftResults AS _ftRow
WITH _ftRow.node AS <root>, (CASE WHEN _ftMax > 0 THEN _ftRow.score / _ftMax ELSE 1.0 END) AS <score>
```

- Divides each hit by the batch max → `[0, 1]`, top hit always `1.0` (a deterministic test anchor).
- `CASE WHEN _ftMax > 0 … ELSE 1.0` is the FalkorDB `maxScore == 0` / NaN guard, applied on **all**
  engines for safety (the consumers only guarded FalkorDB and hit NaN elsewhere later).
- The head's output contract — bind node→rootAlias, normalized score→scoreAlias — is byte-for-byte the
  same shape as `vectorSearchHead`, which is why the builders are near-verbatim mirrors.

Per-engine `CALL`:

| Engine | Procedure | Addressed by |
|---|---|---|
| Neo4j | `db.index.fulltext.queryNodes(name, query)` | index **name** |
| FalkorDB | `db.idx.fulltext.queryNodes(label, query)` | node **label** (no index names) |
| Memgraph | `text_search.search_all(name, query)` | index **name** |

## 4. Codegen

KSP (`drivine4j-codegen`): emits the filtered `loadMatching(query, topK, threshold, spec)` reified
wrapper — for a **view** whose root fragment has a `@FullTextIndex` (`rootFragmentHasFullTextIndex`),
and for a **fragment** that has one (`fragmentHasFullTextIndex`, subject to the same root-only
`emitExtensions` gate the 0.0.67 fragment DSL uses to avoid sealed-hierarchy overload ambiguity). Only
the filtered form is generated; the non-filtered reified `loadMatching<T>` is hand-written.

Java APT: **no change** — Java has no reified extensions and uses the runtime fluent
`query(T).filterWith(TQueryDsl).match(…)` path, which composes with the `<Fragment>QueryDsl` the APT
processor already generates (0.0.67).

## 5. Backend support

Verified cross-engine (Neo4j / FalkorDB / Memgraph) in `FullTextSearchCrossEngineTest`: fragment
ranking + `topK` + normalized `threshold`, the view projection path, a class-level multi-property
index, polymorphic per-node dispatch on a sealed base, and the filtered (full-text + property
predicate) form. Engines with no native full-text index (Neptune / base openCypher) leave
`supportsFullTextSearch = false` and `loadMatching` throws `UnsupportedOperationException`.

**Memgraph note:** text search is **GA** on `memgraph/memgraph:latest` — no experimental flag. (In this
version `--experimental-enabled` only accepts `planner-v2`; passing `text-search` makes the container
refuse to start.) `text_search.search_all(index, query)` yields `node, score`.

**Neo4j note:** full-text indexes populate asynchronously — after seeding, `CALL db.awaitIndexes()`
before searching (the cross-engine test does this for Neo4j only).

## 7. Consumer impact (`embabel-agent-rag-graph`)

The store can delete its entire hand-written full-text Cypher path and call `gom.loadMatching`:

- Delete `RagDialect.chunkFullTextSearchCypher()` / `entityFullTextSearchCypher()` per-engine templates,
  the FalkorDB `CASE WHEN maxScore > 0 … ELSE 1.0` / Neo4j-Memgraph `score/maxScore` normalization, and
  the `$fulltextIndex` / `$chunkLabel` / `$searchText` name-vs-label binding split — all now inside the
  primitive.
- `GraphObjectManagerStore.textSearch` → `gom.loadMatching<ChunkNode>(request.query, request.topK, request.similarityThreshold)`;
  `textSearchWithFilter` → the filtered form (`loadMatching(ChunkNode::class.java, ChunkNodeQueryDsl.INSTANCE, query, topK, threshold) { where { … } }`),
  translating the metadata/entity `PropertyFilter` into `where { }` predicates.
- `cypherSearch.chunkFullTextSearch` / `chunkFullTextSearchWithFilter`, `ChunkSimilarityMapper`, and the
  legacy `resources/cypher/*_fulltext_search.cypher` files become dead — remove them. Combined with
  `loadNearest`, the store's retrieval surface is then **100% object-manager**, no hand-written Cypher.
- One behaviour to preserve: the store phrase-wraps the facet query (`"\"$q\""`) but not the others —
  `loadMatching` does **no** escaping, so keep whatever wrapping the caller relied on at the call site.
- The `@FullTextIndex` the store already declares for schema now drives search too — no new annotation.

## 8. Follow-ups

1. **Query escaping helper** — a small `FullText.escape(userInput)` (or an `escaped: Boolean` flag) so
   callers get safe raw-input search without reinventing Lucene escaping.
2. **`orderBy` on scored results** — `loadMatching` orders by relevance; a secondary sort (e.g. recency
   tie-break) isn't exposed.

_Done in this change:_ the vector + full-text search dispatch was extracted from `GraphObjectManager`
into `VectorSearchPlanner` / `FullTextSearchPlanner` (`ScoredSearchPlanner.kt`), leaving the manager
with thin delegating overloads over one shared `executeScoredSearch` — see §2.
