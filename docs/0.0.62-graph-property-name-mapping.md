# `@GraphProperty` — map a fragment field to a differently-named node property — 0.0.62

Maintainer handoff for `@GraphProperty`: override the **on-disk node-property name** a `@NodeFragment`
field is persisted to and queried by, while the Kotlin field name stays the identity used everywhere
in code. The OGM equivalent of JPA `@Column(name = …)` / Spring Data Neo4j `@Property`. Verified
end-to-end on Neo4j, FalkorDB, and Memgraph.

```kotlin
@NodeFragment(labels = ["ContentElement", "Chunk"])
data class ChunkNode(
    @NodeId val id: String,
    val text: String,
    @GraphProperty("container_section_id") val containerSectionId: String?,
    @GraphProperty("sequence_number")      val sequenceNumber: Long?,
    @VectorIndex val embedding: List<Float>? = null,
)
```

`containerSectionId` reads/writes node property `container_section_id`; `where { … }` filters on
`container_section_id`; a `@RangeIndex` / `@VectorIndex` / `@Unique` on the field indexes the on-disk
name. Everything referenced by the field name in Kotlin is unchanged.

## Why

A consumer promoting structural keys out of an open metadata map into typed fields has those
properties on-disk in **snake_case** (`container_section_id`, `sequence_number`, `root_document_id`, …)
and hand-written traversal Cypher that reads them by those exact names. Idiomatic Kotlin fields are
camelCase. Without a name override the only options were a full data migration or not promoting the
fields — this removes the dilemma.

## The core split: field name is identity, property name is on-disk

`FragmentField` gains `propertyName` (defaults to `name`). The rule threaded through every seam:

- **Identity** (`FragmentField.name`) — bind-parameter names, result-map keys, DSL accessor names,
  session/dirty tracking. Unchanged by an override.
- **On-disk** (`FragmentField.propertyName`) — the written `SET` target, the read projection *source*,
  the id `MERGE`/`WHERE` key, the DSL WHERE left-hand side, and the schema index property.

`FragmentModel.from` reads `@GraphProperty` via both Kotlin reflection (constructor-property
annotations) and Java-field reflection, so Java fragments work too. It exposes
`FragmentModel.nodeIdProperty` (the id field's on-disk name).

## Seams (code map)

| # | Seam | File | What it does |
|---|------|------|--------------|
| 1 | **Write** | `FragmentMergeBuilder` | `SET n.<propertyName> = $<name>` — property decoupled from bind-param. `@VectorIndex` wraps the **param** (`vecf32($name)`) while assigning `<propertyName>`. `@NodeId` MERGE key uses `nodeIdProperty`. |
| 1b | **Batch write** | `BatchSaveOperations` | The UNWIND `SET n += row.props` remaps `row.props` keys to on-disk names and MERGEs on `nodeIdProperty` (no-op remap without overrides). |
| 2 | **Read, concrete** | `FragmentQueryBuilder` | Projection aliases `<name>: n.<propertyName>`; id `WHERE` uses `nodeIdProperty`. |
| 3 | **Read, polymorphic `.*`** | `TransformPostProcessor.reconstructFragmentData` | After concrete-type resolution, renames each override key (`container_section_id` → `containerSectionId`) before `convertValue`. Recurses views. No-op on the concrete path (already field-keyed). |
| 4 | **DSL where** | `PropertyReference` + codegen (`drivine4j-codegen` KSP, `drivine4j-codegen-java` APT) | The generated accessor keeps the field name; its `PropertyReference` carries the **on-disk** name, so `where { chunk.containerSectionId eq x }` renders `chunk.container_section_id = $param`. |
| 5 | **Schema specs** | `FragmentSchemaScanner` | `@VectorIndex` / `@RangeIndex` / `@FullTextIndex` / `@Unique` (property- **and** class-level) build specs on the on-disk name; error messages still name the Kotlin field. |
| 6 | **GraphViews** | `GraphViewProjectionAssembler`, `NestedViewProjector` | Embedded root/relationship-target fragment projections alias `<name>: src.<propertyName>`; the polymorphic `.*` rename (seam 3) already recurses views. |
| 7 | **Vector search read** | `FragmentVectorSearchBuilder`, `VectorIndexResolver` | The `loadNearest` fragment projection aliases field ← property; the resolver searches (and derives the index name from) the **on-disk** embedding name. |

Seam 7's `FragmentVectorSearchBuilder` projection was the one non-obvious miss — vector search has
its own RETURN map, separate from `FragmentQueryBuilder`, and without the alias an overridden
embedding loaded back null (ranking still worked, so it failed quietly). Called out here because it's
the trap the next similar feature will re-encounter.

## The `@VectorIndex` + `@GraphProperty` + `vecf32` interaction (flagged)

All three now key on the on-disk name consistently, so the loop closes:

- schema creates the index on `<propertyName>` (`FragmentSchemaScanner`);
- `save()` writes `SET n.<propertyName> = vecf32($<name>)` on FalkorDB (`FragmentMergeBuilder`);
- `loadNearest` searches `<propertyName>` and derives the index name from it (`VectorIndexResolver`),
  and the projection reads it back into the field (`FragmentVectorSearchBuilder`).

Verified on FalkorDB and Neo4j (`GraphPropertyVectorTest`): index on `embedding_vec`, `vecf32` write
to `embedding_vec`, `loadNearest` ranks and round-trips. **No consumer action needed** — an overridden
embedding "just works", and the Neo4j/Memgraph derived index name shifts to `<label>_<onDiskName>_vector`
(matches on both create and search sides).

## Interactions / edge cases

- **`@GraphProperty` + `@PropertyBag`** on one field → rejected at `FragmentModel.from` (a bag manages
  its own prefixed names).
- **Collision** — two fields resolving to the same on-disk name (via overrides, or an override
  colliding with another field's default) → rejected at `FragmentModel.from`, naming both fields.
- **`@NodeId` override** — flows into the MERGE key, the load `WHERE`, and the batch UNWIND MERGE key.
- **Dirty tracking / session snapshot** — keyed on the Jackson field-name tree, so unaffected; the
  polymorphic `.*` rename (seam 3) restores field names before any snapshot comparison, so no path
  sees on-disk keys.

## One documented deviation (DSL bind-param name)

The DSL bind-param derives from the property path in `CypherGenerator.generateParamName`. With the
on-disk name now in the `PropertyReference`, the internal param becomes `param_chunk_container_section_id_0`
rather than `…_containerSectionId_0`. This is entirely internal — the bindings-map key and the `$ref`
change together and stay aligned, so filtering is correct. Keeping it field-derived would mean
threading a separate param-basis through every `WhereCondition`, which isn't worth it.

## Consumer migration notes

- Promote the snake_case keys to camelCase fields with `@GraphProperty("<snake_case>")`; existing
  on-disk data and hand-written traversal Cypher keep working unchanged.
- An overridden `@VectorIndex` needs no special handling — the index, `vecf32` write, and search all
  follow the on-disk name. If the consumer binds a vector index name as a parameter, note the derived
  name is now `<label>_<onDiskName>_vector`.

## Follow-ups

1. **Naming strategy** (optional, deferred) — a fragment-level or global `SNAKE_CASE` strategy deriving
   the default `propertyName`, with `@GraphProperty` always winning, would remove ~15 per-field
   annotations for the consumer. The explicit override (this deliverable) is the foundation it would
   build on: a strategy only changes how the *default* `propertyName` is computed in
   `FragmentModel.from`.
2. **`@Embedded` value objects** — flattening a nested value object into several prefixed node
   properties (distinct from `@PropertyBag`'s open map) would compose with `@GraphProperty` per
   sub-field; not attempted here.
3. **Class-level composite index property translation** relies on the field→property map; a composite
   `@RangeIndex(properties = […])` naming a field with no override passes through unchanged.
