# Inherited `@NodeId` on sealed subtypes — 0.0.66

Maintainer handoff for a small but load-bearing fix: a concrete `@NodeFragment` that inherits its
`@NodeId` from a supertype getter (`interface X { @get:NodeId val id }`) now resolves its id field, so
it is directly usable — `save`, `load(id)`, snapshot, and rooting a `@GraphView` on it all work.

## The gap (surfaced by the 0.0.65 fixtures)

```kotlin
@NodeFragment(labels = ["ContentElement"])
sealed interface ContentElementNode { @get:NodeId val id: String }

@NodeFragment(labels = ["ContentElement", "Chunk"])
data class ChunkNode(override val id: String, …) : ContentElementNode
```

`FragmentModel.from(ChunkNode).nodeIdField` returned **null**. Kotlin does not propagate a getter
annotation onto an `override`, so the subtype's own property/getter carried no `@NodeId`, and
`findNodeIdField` only inspected the subtype itself. A null id field breaks every direct operation on
the subtype:

- `save(chunkNode)` → "Cannot build MERGE for fragment without @GraphNodeId";
- `load(id, ChunkNode::class)` → no id predicate;
- `loadAll` snapshot → "Cannot snapshot object without @GraphNodeId field";
- a `@GraphView` **rooted** on a concrete subtype → same snapshot failure.

The 0.0.63/0.0.64 polymorphic-view work didn't hit this because those views root on the sealed
**interface** (which carries `@get:NodeId`); the subtypes only appeared as relationship targets /
nested values, where a per-node id isn't extracted. Rooting a view on a concrete subtype — or saving /
loading one directly — is what exposes it.

## The fix

`FragmentModel.findNodeIdField` now treats a property as the id field if `@NodeId` is on the property,
its getter, **or the same-named property/getter on any supertype** (`kClass.allSuperclasses`). One
helper, `hasNodeId(kClass, property)`; the direct-annotation case is unchanged (checked first).

Engine-agnostic (pure model resolution); no generated Cypher changes. Once the id resolves, the merge
builder, query builder, and session snapshot all work unchanged — they only needed a non-null
`nodeIdField` / `nodeIdProperty`.

## Tests

- `model/InheritedNodeIdTest` — a sealed subtype resolves `id` from the interface getter; a directly
  annotated `@NodeId` still resolves.
- `manager/SubtypeDirectUseNeo4jTest` — `save` + `load(id)` of a `DocumentNode` (sealed subtype)
  directly, and a `@GraphView` rooted on `DocumentNode` loads + snapshots.

## Consumer impact

`embabel-agent-rag-graph`'s `ContentElementNode` subtypes (`ChunkNode` / `LeafSectionNode` /
`DocumentNode`) are now first-class: they can be saved and loaded directly and used as a view root, not
only reached polymorphically through the sealed base. No API change.

## Follow-ups

- **Java-fragment interface `@NodeId`** — the Kotlin reflection path (fixed here) covers Kotlin
  fragments; `findNodeIdFieldJava` still walks only superclasses, not interfaces. Java fragments with
  an interface-declared id are niche and unverified; extend the Java fallback if a consumer needs it.
